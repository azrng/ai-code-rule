# AGENTS.md

## 目标
职责划分如下：
- `AGENTS.md`：唯一协作规范来源，统一定义工作规则、任务机制、交付要求
- `backend-AGENTS.md`：后端技术栈、目录结构、实现细则与测试规则
- `doc-AGENTS.md`：设计文档、接口契约与文档维护规则
- `infra-AGENTS.md`：部署、端口、Docker 与交付链路规则
- `CLAUDE.md` / `GEMINI.md`：各 Agent 的入口说明文件，仅负责提醒先读取 `AGENTS.md`，不维护平行规则内容
- `TASK.md`：当前活跃任务与少量最近完成任务的最小记录
- `TaskHistory.md`：兼容提示文件，提示主归档已迁移到 `doc/task-archive/`

---

## 工作方法

1. 输出保持简洁，但分析、实现与交付信息必须完整。
2. 先通过索引、目录和搜索命中相关规则与实现，再按需扩展上下文，不默认全量预读。
3. 回答和交付直接进入有效信息，避免奉承性开头、冗余结尾和低价值复述。

---

## 注意事项
1. 你需要理解用户提出的需求的业务逻辑然后再做设计和开发。
2. 每个接口必须可通过 Swagger 独立验证，返回真实数据。
3. 数据变更操作（增、删、改）必须真实生效，刷新 Swagger 后能看到变化。
4. 接口设计遵循 RESTful 风格，命名清晰，职责单一。

## 子规则阅读顺序

1. 先阅读当前文件，理解全局规则、阶段门控和交付要求。
2. 再根据上方“子规则索引”只补读当前任务命中的子规则文件，不全量预读。
3. 若同时命中多个子规则，优先阅读设计或文档类规则，再阅读实现类规则，最后补充基础设施、联调或交付相关规则。
4. 若任务范围在执行过程中扩大，按新增命中范围继续补读对应子规则。

## 开发流程总览

### 总体阶段划分

所有新功能开发默认按以下阶段推进，阶段之间有明确门控条件：

```text
阶段 0          阶段 1          阶段 2
设计文档   →   后端实现   →   集成测试
（用户确认）   （Codex）       （协作）
```

**例外情况**（AI 自动判断，无需走阶段 0）：
- Bug 修复（功能行为不变，只修正错误）
- 已有接口的文案、注释、轻量返回字段微调
- 配置、环境变量、部署脚本调整
- 单个字段的增删（不涉及新业务流程）

- 阶段 0 设计文档与接口契约细则见 `doc-AGENTS.md`
- 阶段 1 后端实现细则见 `backend-AGENTS.md`
- 阶段 2 集成测试、构建与部署相关约束结合当前文件、`backend-AGENTS.md`、`infra-AGENTS.md` 一起执行

## 使用方式
每个 AI Agent 在开始修改前都必须：
1. 先阅读本文档，确认核心规则、当前开发阶段和入场条件。
2. 按任务范围补充阅读命中的子规则文件；若当前目录包含 `design-system.yaml` 且任务涉及界面规范，再一并阅读。
3. 回读相关模块和现有实现，确认复用点、影响范围与改动边界。
4. 优先复用当前结构；只有现有结构无法承载时再新增文件或抽象。
5. 若任务明显跨多个层次或领域，先拆成子任务，再分别落到对应阶段执行。

### 任务类型阅读策略

- 接口实现、业务逻辑、DTO、EF Core、缓存、Swagger、测试任务优先阅读 `backend-AGENTS.md`
- 需求整理、设计文档、接口契约、devlog 维护任务优先阅读 `doc-AGENTS.md`
- Docker、Compose、环境变量、运行端口、发布验证任务优先阅读 `infra-AGENTS.md`
- 联调或发布收口任务必须同时阅读根 `AGENTS.md`、`backend-AGENTS.md`、`infra-AGENTS.md`

## 核心规则
- 交付必须可直接使用，不能只停留在演示层。
- 不允许新增平行配置体系。
- 不做与当前任务无关的重构。
- 不要猜测问题，要实证排查：通过日志、断点、数据等实际证据定位原因，禁止凭猜测修改代码。
- 所有改动都必须可说明、可验证。

---

## 验证优先级规则

- 验证比指令更重要，能通过测试、构建、Swagger、容器化验证、smoke test 证明的事项，不要只靠文字规则约束。
- 涉及高风险逻辑或易错点时，优先补验证步骤、测试或可复现检查，而不是继续堆叠预防性规则。
- 若本次无法完成验证，必须明确说明未验证项、原因、影响范围和建议下一步。

---

## 思考与实现原则
- 先理解业务目标、用户角色、核心流程，再进行设计和开发。
- 优先选择符合当前需求的最优可行方案，兼顾正确性、可维护性与实现成本。
- 尽可能复用现有代码、结构与组件；只有在明确存在复用价值时才新增抽象。
- 严禁过度设计、过度封装和无意义冗余，避免为单次需求引入不必要的层次和复杂度。
- 代码实现应保持清晰、简洁、稳定，优先保证业务正确性、可读性和后续维护性。
- 单个类、页面、组件、页面基类应保持职责单一，避免巨型文件和巨型类。发现文件持续膨胀、单类职责过多、阅读成本明显升高时，必须优先拆分为更小的组件、服务、辅助类或局部模块。禁止编写超大页面基类、超大工具类、超大 Service 类，禁止把多个无关职责长期堆在同一个类中。
- 遇到需求不清、规则冲突或实现复杂度明显升高时，先说明判断与权衡，再继续执行。

## 编码规则
- 所有源码、配置、文档文件统一使用 `UTF-8` 编码。
- 读取或修改含中文文件时，若出现乱码，先判断是终端显示问题还是文件编码损坏；未确认前禁止覆盖原文件。
- 禁止使用可能隐式改变编码的方式直接改写源码文件，如 shell 重定向、`Out-File`、`Set-Content`。
- Windows / PowerShell 下读取中文文件时，必须显式使用 `UTF-8`。
- PowerShell 命令不接受 `&&`，禁止使用；需要连续执行时改为分步执行或使用 PowerShell 兼容写法。
- 如果编写注释（含代码注释、文档注释、XML 注释等），统一使用中文，不使用纯英文注释；必要的英文标识、协议字段名或框架关键字可保留原文。
- 修改含中文内容后，必须重新读取一次并确认关键中文显示正常。

## 任务管理机制
`TASK.md` 与 `doc/task-archive/` 共同组成任务记录体系：`TASK.md` 只维护当前仍需关注的任务与少量最近完成任务的最小记录，较早的 `DONE` 任务按月归档到 `doc/task-archive/YYYY-MM.md`；`TaskHistory.md` 仅保留兼容提示，不再作为主归档文件。

### 任务状态
- `TODO`：未开始
- `DOING`：进行中
- `BLOCKED`：被阻塞
- `REVIEW`：已完成开发，等待确认
- `DONE`：已完成

### 执行规则
1. 开始工作前，先查看 `TASK.md` 是否已有对应任务。
2. 如果已有任务，优先更新原任务，不重复新建。
3. 如果没有任务，在 `TASK.md` 中新增最小任务记录。
4. 开始执行时，将任务状态更新为 `DOING`。
5. 若任务无法继续，更新为 `BLOCKED` 并写明原因。
6. 开发完成但仍需确认时，更新为 `REVIEW`。
7. 验证完成并确认交付后，更新为 `DONE`。
8. 当 `TASK.md` 中任务总数超过 20 条，或 `DONE` 任务超过 10 条时，将较早完成的 `DONE` 任务迁移到对应月份的 `doc/task-archive/YYYY-MM.md`。
9. 归档时仅允许迁移 `DONE` 任务，`TODO`、`DOING`、`BLOCKED`、`REVIEW` 任务必须保留在 `TASK.md`。
10. 归档任务时保留原任务 ID、任务信息与最近更新时间，并在归档文件中补充 `归档日期`。
11. `TaskHistory.md` 仅保留兼容提示；发生任务归档时，在 `doc/devlog/` 中补充一份简短归档说明，记录迁移范围与触发原因。

### 每个任务至少包含
- 任务 ID
- 任务名称
- 任务目标
- 当前阶段
- 负责人 AI
- 任务状态
- 优先级
- 最近更新时间

### AI Agent 要求
- 任务状态或验收口径发生变化时，及时同步到 `TASK.md`。
- 触发归档阈值时同步维护 `doc/task-archive/`，并确认 `TaskHistory.md` 的兼容提示仍然有效。
- 范围变化时同步补充任务说明、验收标准和风险。
- 每次开发完成后，都需要在 `doc/devlog/` 下新增一份本次开发简短说明的 Markdown 记录。

## Git 与提交流程

### 分支命名
- `feat/<desc>`：新功能
- `fix/<desc>`：缺陷修复
- `refactor/<desc>`：无行为变更的重构
- `chore/<desc>`：工具、依赖、配置调整
- `docs/<desc>`：仅文档变更

### Commit 规范
- 提交信息优先采用 Conventional Commits：
  - `<type>(<scope>): <简短描述>`
- 示例：
  - `feat(auth): add refresh token endpoint`
  - `fix(user): correct pagination count`
  - `chore(dotnet): pin NuGet package version`

### 交付前自查
- 后端：编译（`dotnet build`）、测试（`dotnet test`）
- 涉及数据库结构变更时已确认迁移脚本
- 新增环境变量已同步更新相关文档
- 涉及 Docker 时已确认构建或部署链路

### 提交触发规则
- 每次修改完后都必须提交代码。
- 若本次开发生成了本地运行产物、缓存、测试数据库、构建产物或依赖目录，应同步检查并更新 `.gitignore`。

## 交付收口规范
- 当用户请求“开始开发”而非“只出方案”时，AI Agent 在实现完成后应默认继续做交付收口。
- 交付收口时，先完成“交付前自查”中的适用检查，再按实际情况补充发布构建、启动验证与应用级 smoke test。
- 收口阶段同步检查文档、`TASK.md`、`doc/devlog/` 与必要的忽略文件是否需要更新。
- 若某项验证未执行，最终输出必须明确说明未执行项、原因、影响范围和建议下一步。

---

## 高风险操作确认规则

- 删除文件、删除目录、批量重构、数据库破坏性变更、清理运行环境前，必须先得到明确确认。
- 无法确定影响范围时，不要直接执行高风险操作，应先说明风险和可回滚方案。
- 对可能影响现有数据、历史文件或本地环境的操作，优先提供最小影响方案。

---

## 常见禁止事项
- 禁止在 Controller 层编写业务逻辑，应放入 Service。
- 禁止修改数据模型后不补迁移脚本。
- 禁止在异步代码中使用阻塞式等待（`.Result` / `.Wait()`）。
- 禁止绕过既有提交校验流程，如 `git commit --no-verify`。
- 禁止直接使用 EF Core Migrations，应使用 `Azrng.SqlMigration`。
- 禁止直接操作 Redis，必须通过 `IRedisProvider` 接口。
- 禁止手动配置依赖注入，应使用标记接口方式（`ITransientDependency` / `IScopedDependency` / `ISingletonDependency`）。
- 禁止返回非 `ResultModel` 包装的响应格式。
- 禁止抛出非 Azrng 体系的自定义异常。
- 禁止在同一个 C# 源文件中声明多个顶层类型；一个 `.cs` 文件只允许包含一个顶层 `class`、`interface`、`abstract class`、`record`、`enum` 等定义。
- 禁止未经确认直接执行删除文件、批量重构、数据库破坏性变更或环境清理。

## 交付输出要求
最终输出优先使用中文，并至少说明：
- 本次改了什么
- 核心实现方式
- 修改了哪些文件
- 已执行和未执行的校验
- 当前任务状态
- 风险、阻塞或假设
- 是否已更新 `doc/devlog/`

---

## 重复错误回顾与规则更新机制

- 当 AI 在同一类问题上连续出现两次错误时，必须触发一次简短回顾分析。
- 回顾至少应说明：错误现象、根因、原规则缺口、后续如何避免再次发生。
- 回顾结论必须落实到当前架构目录的 `AGENTS.md` 或对应子规则文件中，不能只停留在对话说明。
- 回顾分析的简短记录格式见 `doc-AGENTS.md`。
- 若本次回顾导致规则模板发生变更，必须同步新增一条 `devlog/` 记录。
