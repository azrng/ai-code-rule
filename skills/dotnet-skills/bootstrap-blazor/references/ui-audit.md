# BootstrapBlazor UI 审查清单

仅在用户要求审查、评审或验收 Blazor UI 时阅读。本清单补充 API 正确性检查，不替代项目自己的设计系统、权限模型或测试规范。

## 1. 先确认基础运行条件

- `AddBootstrapBlazor()`、静态 CSS/JS、`_Imports.razor` 与同一交互 circuit 内的 `<BootstrapBlazorRoot>` 是否齐全。
- `Table` 只能二选一使用 `Items` 或 `OnQueryAsync`；服务端分页应返回正确的 `QueryData<T>` 与 `TotalCount`。
- 若项目使用自定义 Layout、导航或 CSS，不要求改成 `<Layout>` / `<Menu>`；审查其键盘可达性、焦点可见性、小屏行为和选中状态即可。

## 2. 写入与表单

- 新建、编辑、设置等会持久化数据的表单，应有可验证的必填、范围和格式规则。优先使用 `<ValidateForm Model ... OnValidSubmit>`、模型 DataAnnotations 或已确认的 `ValidateRules`；提交在弹窗 footer 时，确认它仍在 `<form>` 内，或显式 `await form.ValidateAsync()`。
- 每个异步写入都要防止重复提交：提交期间禁用同一动作，并在成功或失败后恢复。网络或持久化失败必须有用户可见的内联错误或 Toast，不能仅记录日志。
- 删除、重置密钥、停用等高影响动作应在真正执行前确认；表格行内优先 `<TableCellPopConfirmButton>`，其他场景可用已验证的 Modal / Swal。

## 3. 数据、状态与反馈

- 每个数据页检查 loading、empty、error 三态。加载时间明显时优先 `Skeleton` 或局部 `Spinner`，不要让用户只能看到空白区域。
- 筛选、查询、刷新和自动刷新应说明当前范围/最后更新时间；自动刷新不能覆盖用户正在编辑的内容。
- 表格行点击打开详情时，应保留可见的“详情”入口，不能只依赖鼠标手势；抽屉和弹窗应可关闭并恢复焦点。

## 4. 导航、可访问性与小屏

- 原生交互必须用语义化 `<button>` / `<a>`，带清晰名称；图标按钮提供文本、`aria-label` 或可访问名称，装饰图标使用 `aria-hidden="true"`。
- 自定义移动侧栏要可通过键盘打开/关闭，能用 Escape 关闭，打开时具有明确的背景层/焦点管理，且导航后收起。
- 在 375px、768px 和桌面宽度审查：筛选器和操作按钮可换行；宽表支持可理解的横向滚动或紧凑替代；固定控件不遮挡主要内容。

## 输出分级

- **P0/P1**：会造成未授权访问、错误提交、重复写入、数据误删或主要交互不可用的问题。
- **P2**：明显降低可访问性、移动可用性或错误恢复能力的问题。
- **P3**：信息层级、密度、文案、视觉一致性等改进建议。

每项指出文件和行号、观察到的证据、对用户的影响，以及最小改法。无法访问认证后的页面时，明确说明未验证的状态，不把推测当作结论。
