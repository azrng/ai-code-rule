# 管理操作审计日志

**使用场景**：需要追溯谁在何时对用户、角色、配置或其他管理资源执行了什么操作，并在 Blazor 管理端查询这些记录。

## 先界定日志用途

- 审计日志记录可归因的管理行为；请求访问日志、应用诊断日志、业务事件和指标各有用途，按项目需要分开存储与授权。
- 先确定需要覆盖的操作、保留期限、访问角色、导出要求和审计完整性要求。不要默认记录所有请求正文或所有数据库变更。
- 记录模型通常包含事件时间（建议 UTC）、操作者 ID/显示名、动作、资源类型与标识、结果、简短摘要，以及按需使用的来源地址和关联 ID。字段按查询和调查需求取舍。
- 对变更前后内容优先记录经过筛选的字段差异或业务摘要。密码、令牌、密钥、认证头、完整请求体及其他敏感数据不得写入日志。

## 写入与完整性

- 在服务端可信的业务操作入口记录事件，不依赖浏览器上报操作者或结果；操作者从已认证身份解析，匿名或系统任务应使用明确的主体类型。
- 仅在明确操作结果后记录成功或失败，并使动作、结果和摘要能够区分创建、修改、删除、启停、授权变更等行为。避免把一次批量操作记录成无法解释的单条通用消息。
- 根据风险选择日志失败策略：若审计是操作成功的合规前提，应将业务变更与审计写入放入同一事务，或采用可靠 Outbox 等机制；若允许审计暂时不可用，则记录告警并明确存在审计缺口。不要默默吞掉异常，也不要在没有业务决策时一律阻断或放行操作。
- 审计记录通常应追加写入；限制修改和删除权限，并为保留期清理、归档和导出定义明确授权与留痕。
- 为常用过滤与排序字段建立适当索引。大表查询使用服务端分页、上限和稳定排序，避免一次加载全部记录。

## Blazor 查询界面

- 使用 `Table` 展示时间、操作者、动作、资源、结果和摘要；按数据量调用服务端分页查询。
- 提供与调查场景匹配的过滤项，例如时间范围、操作者、动作、资源类型/标识和结果；组合过滤条件应由后端校验并执行。
- 详情视图只展示允许披露的字段或脱敏后的差异。避免把未经处理的结构化数据直接渲染到页面。
- 审计日志页面本身也需要授权。导出、查看详情、归档清理等能力可有更严格的权限，并对这些操作再次留痕。
- 区分加载中、无记录、查询失败和无权限状态；日期时区应明确展示，避免把 UTC 时间误当成本地时间。

## 验证清单

- 关键成功和失败操作都有正确的操作者、动作、资源、时间与结果；系统任务和匿名操作也能识别来源。
- 注入或变更客户端操作者字段不能伪造审计主体；未授权用户不能查询、导出或删除记录。
- 密码、令牌、密钥和未授权字段不会出现在摘要、异常文本、差异内容或导出文件中。
- 分页、过滤、稳定排序、时间边界和大数据量查询符合预期；审计存储失败行为符合已选定的完整性策略。
