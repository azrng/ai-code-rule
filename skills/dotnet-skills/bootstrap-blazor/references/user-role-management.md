# 用户、角色与权限管理

**使用场景**：Blazor 管理端需要管理用户、角色、菜单或业务权限，并限制页面、操作或资源访问。

## 先确认授权模型

- 先查项目已有的认证方式、授权策略、用户/角色模型、权限缓存和数据范围约定；沿用现有机制，不在 UI 层另造一套授权状态。
- 明确单个用户是否可以绑定多个角色（一对多视角）、多个用户是否可以共享同一角色，以及权限按页面/功能/数据范围如何划分、角色变更何时生效。若角色可被多个用户共享，则用户与角色整体是多对多关系，持久化时使用关联实体或关联表；不要因 UI 使用树或矩阵就推断数据库关系模型。
- 集中维护稳定的权限键及其名称、分组、说明和是否允许分配等元数据。展示名称可调整，权限键应保持稳定；菜单项只是权限展示的一种映射，不应成为唯一授权来源。
- 区分认证与授权：已登录不代表可以执行所有管理操作。优先复用 ASP.NET Core 的 policy、claim 或 resource-based authorization，并把权限检查放在服务端入口。

## 用户管理页面

- 用户列表展示识别账号所需的信息、状态、当前角色和最近活动；按数据量采用服务端或本地分页，并提供常用筛选。
- 一个用户绑定多个角色时，创建和编辑用户使用多选控件，列表清楚展示全部已绑定角色；选项来自服务端可分配角色目录。若业务采用每个用户仅一个角色的模型，则使用单选控件并沿用既有数据关系。
- 用户角色集合的保存、替换和单角色撤销都作为明确业务操作处理；说明多个角色的有效权限如何合并，以及角色冲突的处理规则。
- 如果接入的既有项目明确限制每个用户只能绑定一个角色，沿用其单选模型，不擅自改动数据关系。
- 停用、删除、重置凭据等高风险操作需有确认和结果反馈。保护最后一个可用管理员等约束必须在服务端执行。

## 角色与菜单授权页面

- 角色列表展示名称、说明、内置状态、成员数量和已授权菜单数量；创建、编辑和删除入口受当前操作者权限控制。
- 角色编辑表单包括名称、说明和菜单权限矩阵。菜单按导航分组呈现，支持分组全选/取消，并显示不可分配或系统保留项。
- 权限目录由稳定键、显示名称、分组、关联路由和可分配策略组成。路由改名或菜单重排不应意外更改权限身份。
- 将角色授权保存为明确的角色-菜单关系；如同时存在按钮权限、API 权限或数据范围权限，应分开说明并分别授权，不要把菜单可见性当成完整授权。
- 保存后展示实际生效结果；如果导航来自角色权限，应在当前授权刷新后更新菜单。不要只更新前端缓存而遗漏服务端授权状态。

## 典型管理校验

- 保存时在应用服务中校验名称唯一、权限键有效、角色可分配范围和用户/角色关联。UI 校验用于及时反馈，不能替代服务端校验。
- 删除角色前检查引用关系。仍被用户使用时，应拒绝删除并说明如何解除引用，或要求操作者显式选择迁移目标；不要静默遗失授权。
- 对内置角色、系统保留权限及最后一个有效管理员等关键约束，在所有写入入口统一执行，而不是只在 Blazor 页面禁用按钮。

## 授权边界

- 页面级授权可使用路由授权或 `AuthorizeView` 控制可见性；按钮级授权可隐藏或禁用无权操作，并说明原因。
- 页面、按钮和菜单的显隐只改善交互，不构成安全边界。事件处理器、应用服务、Minimal API/Controller 以及资源读取和写入入口都必须验证权限。
- 对记录归属、组织范围或资源状态等上下文相关规则，使用资源级授权或应用服务规则；不能只检查角色名或前端传入的权限列表。
- 不信任客户端提交的角色、权限、用户 ID 或资源范围。服务端应从可信身份和当前授权数据重新解析并校验。
- 权限撤销和账号停用应在项目所需时限内生效。检查 Cookie/Token 生命周期、内存缓存、Blazor Server circuit 与多实例缓存失效；避免旧会话长期保留已撤销权限。

## Blazor 页面注意事项

- 管理列表优先使用 BootstrapBlazor `Card` + `Table<TItem>`，通过 `TableColumns` / `RowButtonTemplate` 表达列和行操作；分页查询接 `OnQueryAsync`，避免只套视觉 CSS 的原生 `<table>` 替代组件。
- 表单优先使用 `BootstrapInput`、`Select`、`CheckboxList`、`EditForm` 和 `Modal`；用户多角色绑定使用多选控件，角色菜单授权抽为可复用的分组 `PermissionMatrix` 组件，权限键保持稳定。
- 状态和角色类型使用 `Badge`，主要及次要操作使用 BootstrapBlazor `Button`；按需复用 `table.md`、`forms.md`、`modal.md`、`layout-menu.md` 和 `treeview-toast.md` 中的具体 API。
- 保存、删除和角色变更失败时显示可理解的错误；并发编辑时提示数据已变化并允许重新加载，避免覆盖其他管理员的修改。
- 加载角色或权限目录时显示加载状态；无权限、无数据和加载失败应区分呈现。
- 角色变更成功后刷新当前页面需要的数据，并按项目授权生效策略更新认证状态或提示重新登录。

## 验证清单

- 无权用户直接请求页面、事件、服务或 API 均被拒绝，而不只是看不到导航项。
- 越权权限键、被保护角色修改、删除仍有引用的角色及管理员锁死场景均由服务端拦截。
- 用户管理页可按项目模型绑定/调整用户角色；角色管理页可创建/编辑角色并按导航分组绑定菜单权限。
- 单角色/多角色、权限撤销时效和缓存更新符合项目现有模型及安全要求。
- 权限矩阵的全选、取消、保存失败和重新加载行为正确，未授权的数据不会因 UI 隐藏而被误认为安全。
