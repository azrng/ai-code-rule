# AGENTS.md

## 目标
职责划分如下：
- `AGENTS.md`：唯一协作规范来源，统一定义工作规则、任务机制、交付要求
- `backend-AGENTS.md`：Python/FastAPI 技术栈、项目结构、后端实现与测试规则
- `doc-AGENTS.md`：需求记录、devlog 与文档维护规则
- `infra-AGENTS.md`：Docker、运行环境与交付链路规则
- `CLAUDE.md` / `GEMINI.md`：各 Agent 的入口说明文件，仅负责提醒先读取 `AGENTS.md`，不维护平行规则内容
- `TASK.md`：当前活跃任务与少量最近完成任务的最小记录
- `TaskHistory.md`：兼容提示文件，提示主归档已迁移到 `doc/task-archive/`

---

## 工作方法

1. 行动前先思考，写代码前先阅读现有文件并理解业务目标。
2. 输出保持简洁，但分析与落地必须完整。
3. 优先编辑现有文件，而不是无差别重写。
4. 已确认无变更风险的文件无需重复阅读，但遇到上下文缺口时必须补读。
5. 完成前尽量执行可落地的校验，无法执行时明确说明原因和影响。
6. 避免奉承性开头或冗余结尾，直接进入有价值的信息。
7. 保持解决方案简单直接，避免过度设计。
8. 用户指令始终优先于本文件内容。
9. Windows / PowerShell 场景下命令不接受 `&&`，禁止使用；需要连续执行时改为分步执行或使用 PowerShell 兼容写法。

## 注意事项
1. 先理解用户提出的业务目标、系统边界和调用链，再设计 API、数据模型与任务流程。
2. 所有接口、脚本、任务调度与数据处理逻辑都必须真实可执行，不能只停留在示例或伪代码层。
3. 业务逻辑、HTTP 编排、数据访问和外部集成要分层清晰，避免把复杂逻辑堆在入口文件中。
4. 涉及新增、修改、删除或异步任务的行为必须可验证，重启服务、重跑任务或重新请求后仍能看到真实结果。
5. 复杂系统优先先搭建项目骨架、配置、依赖与基础能力，再按模块逐步实现，不一次性铺开全部功能。

## 开发流程总览

### 总体阶段划分

Python 后端模板默认按以下顺序推进：

```text
阶段 0          阶段 1          阶段 2
需求确认   →   后端实现   →   集成验证
（用户确认）   （Codex）       （协作）
```

**例外情况**（AI 自动判断，无需单独补设计说明）：
- Bug 修复（功能行为不变，只修正错误）
- 配置、环境变量、部署脚本调整
- 单个字段或响应文案的轻量调整

- 后端实现与测试细则见 `backend-AGENTS.md`
- 文档维护细则见 `doc-AGENTS.md`
- 运行环境与容器化细则见 `infra-AGENTS.md`

## 编码与注释规则
- 所有源码、配置、文档文件统一使用 `UTF-8` 编码。
- Windows / PowerShell 场景下命令不接受 `&&`，禁止使用；需要连续执行时改为分步执行或使用 PowerShell 兼容写法。
- 如果编写注释（含代码注释、文档注释、docstring 等），统一使用中文，不使用纯英文注释；必要的英文标识、协议字段名或框架关键字可保留原文。
- 单个类、页面、组件、页面基类应保持职责单一，避免巨型文件和巨型类。发现文件持续膨胀、单类职责过多、阅读成本明显升高时，必须优先拆分为更小的组件、服务、辅助类或局部模块。禁止编写超大页面基类、超大工具类、超大 Service 类，禁止把多个无关职责长期堆在同一个类中。

## 任务管理机制
`TASK.md` 与 `doc/task-archive/` 共同组成任务记录体系：`TASK.md` 只维护当前仍需关注的任务与少量最近完成任务的最小记录，较早的 `DONE` 任务按月归档到 `doc/task-archive/YYYY-MM.md`；`TaskHistory.md` 仅保留兼容提示，不再作为主归档文件。

### 任务状态
- `TODO`：未开始
- `DOING`：进行中
- `BLOCKED`：被阻塞
- `REVIEW`：已完成开发，等待确认
- `DONE`：已完成

### 执行规则
1. 开始工作前，先查看 `TASK.md` 是否已有对应任务。
2. 如果已有任务，优先更新原任务，不重复新建。
3. 如果没有任务，在 `TASK.md` 中新增最小任务记录。
4. 开始执行时，将任务状态更新为 `DOING`。
5. 若任务无法继续，更新为 `BLOCKED` 并写明原因。
6. 开发完成但仍需确认时，更新为 `REVIEW`。
7. 验证完成并确认交付后，更新为 `DONE`。
8. 当 `TASK.md` 中任务总数超过 20 条，或 `DONE` 任务超过 10 条时，将较早完成的 `DONE` 任务迁移到对应月份的 `doc/task-archive/YYYY-MM.md`。
9. 归档时仅允许迁移 `DONE` 任务，`TODO`、`DOING`、`BLOCKED`、`REVIEW` 任务必须保留在 `TASK.md`。
10. 归档任务时保留原任务 ID、任务信息与最近更新时间，并在归档文件中补充 `归档日期`。
11. `TaskHistory.md` 仅保留兼容提示；发生任务归档时，在 `doc/devlog/` 中补充一份简短归档说明，记录迁移范围与触发原因。

### 每个任务至少包含
- 任务 ID
- 任务名称
- 任务目标
- 当前阶段
- 负责人 AI
- 任务状态
- 优先级
- 最近更新时间

### AI Agent 要求
- 开始任务前先同步任务状态。
- 开发过程中及时更新 `TASK.md`。
- 触发归档阈值时同步维护 `doc/task-archive/`，并确认 `TaskHistory.md` 的兼容提示仍然有效。
- 范围变化时同步补充任务说明、验收标准和风险。
- 每次开发完成后，都需要在 `doc/devlog/` 下新增一份本次开发简短说明的 Markdown 记录。

## Git 与提交流程

### 分支命名
- `feat/<desc>`：新功能
- `fix/<desc>`：缺陷修复
- `refactor/<desc>`：无行为变更的重构
- `chore/<desc>`：工具、依赖、配置调整
- `docs/<desc>`：仅文档变更

### Commit 规范
- 提交信息优先采用 Conventional Commits：
  - `<type>(<scope>): <简短描述>`
- 示例：
  - `feat(api): add order approval endpoint`
  - `fix(task): correct retry scheduling`
  - `chore(docker): align uvicorn startup command`

### 交付前自查
- 代码检查：`ruff check`、`ruff format`
- 测试：`pytest`
- 涉及数据库结构变更时确认 Alembic 迁移（若使用数据库）
- 新增环境变量已同步更新 `.env.example`
- 涉及容器交付时已验证 Docker 构建

### 提交触发规则
- 每次修改后必须提交
- 若本次开发生成了缓存、测试数据库、构建产物或依赖目录，应同步检查并更新 `.gitignore`

## 交付收口规范
- 当用户请求“开始开发”而非“只出方案”时，AI Agent 在实现完成后应默认继续做交付收口。
- 交付收口至少应按实际情况依次检查：
  1. 编译 / 测试
  2. 构建
  3. 发布构建与启动验证
  4. 应用级 smoke test
  5. 文档、`TASK.md`、`doc/devlog/`、忽略文件更新
- 若某项验证未执行，最终输出必须明确说明未执行项、原因、影响范围和建议下一步。

## 常见禁止事项
- 禁止在 API 路由函数中编写业务逻辑，必须通过服务层处理
- 禁止在服务层直接返回 ORM 模型，必须转换为 Pydantic Schema
- 禁止在异步代码中使用同步阻塞调用
- 禁止跳过 Alembic 直接手动修改数据库结构（使用数据库时）
- 禁止直接使用同步 Redis 客户端，异步项目必须使用异步方案
- 禁止在代码中硬编码配置值，必须通过配置体系管理
- 禁止提交 `print()` 调试语句，统一使用日志
- 禁止在测试中调用真实第三方服务
- 禁止凭猜测修改代码排查问题，必须通过日志、断点、数据等实际证据定位原因
