# AGENTS.md

## 适用范围

- 作用域：仓储、数据访问、依赖注入、配置、构建发布与交付验证规则
- 触发场景：涉及 Repository、数据库、依赖注入、配置、启动方式、打包发布时阅读

### 阅读摘要
- 建议阅读：改仓储、改数据访问、改依赖注入、改配置、改发布链路
- 可先跳过：纯界面样式、纯业务编排、仅文档整理
- 优先查看：数据访问 / 配置规则、构建发布规则、`提交前最小回归`

### 常见任务入口
- 改 Repository 或数据库结构：先看数据访问规则与迁移约束
- 改依赖注入、配置、连接串：先看配置规则与运行约束
- 改构建、发布、打包流程：先看交付规则与验证要求
- 补基础设施回归：先看 `提交前最小回归`

## 技术选择原则
如果仓库已经有真实实现，以现有代码为准，不要强行重构或替换技术栈。

**技术债务评估框架**：
- **沿用现有实现**：代码可正常运行、无明显性能问题、维护成本可接受、团队熟悉度高
- **必须重构**：存在安全漏洞、严重影响性能、阻碍新功能开发、维护成本过高
- **可选重构**：代码风格不一致、存在更好的替代方案、但不紧急
- **禁止重构**：仅为个人偏好、追赶技术潮流、非关键路径的过度优化

**重构决策流程**：
1. 先评估现有代码的技术债务等级（高 / 中 / 低）。
2. 判断重构的紧急程度和业务价值。
3. 评估重构风险和工作量。
4. 高风险或大规模重构需先与团队确认。

## 基础设施规则

### Repository 层规则（可选，仅在使用数据库时）
- 仓储类必须实现接口，接口定义在 `Repositories/Interfaces/` 目录
- 仓储只负责数据访问与查询拼装，不承担业务流程编排
- 仓储方法必须是异步的，支持取消令牌
- 涉及事务时，使用 `IDbTransaction` 或等价事务边界统一管理
- 仓储实现注册到 DI 容器时，统一复用现有批量注册方式

### 数据访问规则（可选，仅在使用数据库时）
- 数据库连接字符串从配置文件读取，禁止硬编码
- 数据库连接必须使用 `using` 或等价机制管理生命周期
- Dapper 映射通过 `Column` 特性或集中式映射处理
- 所有查询必须使用参数化查询，禁止拼接 SQL
- 数据库字段命名使用 snake_case

### 依赖注入与配置规则
- Repository、基础设施服务和外部集成统一通过依赖注入提供
- 不要在 ViewModel、页面或应用层手动 new 出数据库连接、仓储实现或外部客户端
- 配置项统一通过现有配置体系读取，不要新增平行配置入口
- 若新增外部服务接入，必须补充对应配置说明与默认占位

### 迁移与持久化规则（可选，仅在使用数据库时）
- 涉及数据库结构变更时，同步生成并维护迁移脚本
- 迁移脚本必须进入版本控制，不允许只改实体或 SQL 而不补迁移说明
- 若包含初始化数据、回填逻辑或数据修复，必须补充 devlog 说明影响范围
- 迁移执行顺序、回滚方式和版本号命名要保持一致

## 构建与发布规则

### 构建规则
- 优先复用现有解决方案、发布配置和构建脚本
- 构建前确认引用、配置文件、资源文件和迁移脚本已被正确纳入输出
- 若项目包含数据库文件、模板资源或本地依赖，需明确复制策略与目标目录

### 发布规则
- 生产发布优先采用单文件发布（Single File Publish）或当前仓库既有发布方式
- 不要把密钥写入配置文件或发布包
- 发布链路要可追踪，至少能定位版本号、构建时间和核心变更来源
- 清理旧版本时要保留最小回滚窗口

### 发布交付规则
- 只要本次任务涉及发布配置、版本号和启动命令，完成实现后应主动执行一次构建验证
- 若因环境限制无法执行，必须明确说明
- 发布验证至少包括：
  - 构建是否成功
  - 应用是否成功启动
  - 关键功能是否处于可用状态
  - 核心访问链路是否可用

## 测试规则

### 总体要求
- 影响行为的改动应优先补充或更新测试，而不是只修改实现代码
- 若本次改动未补测试，必须在最终说明中写明原因和风险
- 测试应覆盖真实基础设施行为，不要只验证空壳调用

### 基础设施测试
- Repository 层 SQL 查询、数据映射、事务处理发生变化时，应补充对应测试
- 配置绑定、迁移执行、连接初始化等关键基础设施逻辑发生变化时，应补充验证
- 若无法做自动化测试，至少补充一次可复现的手工验证步骤

### 外部依赖与数据
- 测试中不要真实调用不可控外部服务，统一使用 mock、stub 或本地替身
- 测试数据应尽量最小化、可读、可重复执行
- 不要让测试依赖本地人工状态或手工残留数据库

### 无法执行测试时
- 必须说明未执行的测试类型
- 必须说明未执行原因
- 必须说明潜在影响范围和风险


### 提交前最小回归
- 修改 Dockerfile、Compose、启动命令、打包脚本或端口映射时：至少执行一次构建与启动验证
- 修改环境变量、配置项或连接串时：确认示例配置、文档和运行方式同步更新
- 修改数据库、仓储、依赖注入或外部服务集成时：至少补一项真实链路或等价验证
- 若本次改动同时影响应用访问链路，应至少补一次核心链路检查
