# AGENTS.md

## 目标
职责划分如下：
- `AGENTS.md`：唯一协作规范来源，统一定义工作规则、任务机制、交付要求
- `frontend-AGENTS.md`：Next.js 页面、组件、状态、路由、样式与前端测试规则
- `backend-AGENTS.md`：Next.js Route Handlers、Server Actions、Prisma 与服务端测试规则
- `doc-AGENTS.md`：设计文档、接口契约、设计系统与文档维护规则
- `infra-AGENTS.md`：部署、端口、Docker 与交付链路规则
- `CLAUDE.md` / `GEMINI.md`：各 Agent 的入口说明文件，仅负责提醒先读取 `AGENTS.md`，不维护平行规则内容
- `design-system.yaml`：设计 token 与 UI 规范
- `TASK.md`：当前活跃任务与少量最近完成任务的最小记录
- `TaskHistory.md`：归档历史 `DONE` 任务的最小记录

---

## 工作方法

1. 行动前先思考，写代码前先阅读现有文件并理解业务目标。
2. 输出保持简洁，但分析与落地必须完整。
3. 优先编辑现有文件，而不是无差别重写。
4. 已确认无变更风险的文件无需重复阅读，但遇到上下文缺口时必须补读。
5. 完成前尽量执行可落地的校验，无法执行时明确说明原因和影响。
6. 避免奉承性开头或冗余结尾，直接进入有价值的信息。
7. 保持解决方案简单直接，避免过度设计。
8. 用户指令始终优先于本文件内容。

---

## 注意事项
1. 你需要先理解用户提出的业务需求和使用场景，再进行页面、数据模型与交互设计。
2. 你需要根据功能需求设计多级菜单、权限边界和导航结构，管理员默认拥有全部菜单权限。
3. 功能模块必须具备可直接操作的完整页面，而不是只做静态展示或只保留占位。
4. 所有关键按钮、表单、筛选、分页、详情、状态切换等交互都必须可用，页面内容应尽量完整，不能只停留在演示层。
5. 系统必须包含登录页，并提供默认应用图标、应用名称和统一的基础布局；登录页左上角应展示应用图标与名称。
6. 界面应具备适度动效与清晰层级，视觉风格需要符合企业业务系统“专业、可信、简洁”的审美要求。
7. 涉及新增、修改、删除等业务逻辑时，必须能够真实生效并持久化。阶段 1 可以临时使用 mock 数据，但进入阶段 2/3 后必须接入真实服务端逻辑与数据库链路。
8. 由于系统模块通常较多，优先先搭建 Next.js 应用骨架、布局和基础能力，再按子模块逐步实现，而不是一次性铺开全部功能。

## 开发流程总览

### 总体阶段划分

所有新功能开发必须严格经历以下四个阶段，阶段之间有明确的门控条件，不满足条件不得进入下一阶段：

```text
阶段 0          阶段 1            阶段 2                阶段 3
设计文档   →   页面与交互实现   →   服务端与数据实现   →   联调与交付
（用户确认）    （Claude Code）      （Codex）             （协作）
```

**例外情况**（AI 自动判断，无需经过阶段 0）：
- Bug 修复（功能行为不变，只修正错误）
- 已有页面的样式、文案微调
- 配置、环境变量、部署脚本调整
- 单个字段的增删改（不涉及新页面或新业务流程）

- 阶段 0 设计文档与接口契约细则见 `doc-AGENTS.md`
- 阶段 1 前端实现细则见 `frontend-AGENTS.md`
- 阶段 2 后端实现细则见 `backend-AGENTS.md`
- 阶段 3 联调与部署相关约束结合当前文件和 `infra-AGENTS.md` 一起执行

## 使用方式
每个 AI Agent 在开始修改前都必须：
1. 先阅读本文档，理解核心规则和流程
2. 确认当前处于哪个开发阶段，检查该阶段的入场条件是否满足
3. 再阅读 `design-system.yaml`
4. 再按任务命中范围阅读对应子规则文件
5. 再阅读相关模块与现有实现
6. 优先复用当前结构，再决定是否新增文件
7. 不要每次预读所有文件，优先通过索引、目录和搜索定位命中的文件后再阅读
8. 先读根文件中的子规则索引，再读命中的子规则文件，不要全量加载所有规则文件

### 任务类型阅读策略

- 前端任务优先阅读 `frontend-AGENTS.md`
- 后端任务优先阅读 `backend-AGENTS.md`
- 设计文档、接口契约、设计系统、devlog 维护任务优先阅读 `doc-AGENTS.md`
- Docker、Compose、环境变量、运行端口、发布验证任务优先阅读 `infra-AGENTS.md`
- 联调任务必须同时阅读根 `AGENTS.md`、`frontend-AGENTS.md`、`backend-AGENTS.md`、`infra-AGENTS.md`
- 若任务明显跨前后端，先拆成子任务再执行，不要把前后端实现混在一个步骤里

## 核心规则
- 先理解，再修改。
- 先复用，再新增。
- 优先 Server Component，最小化 Client Boundary。
- 业务逻辑必须可说明、可测试、可验证。
- 不允许新增平行配置体系或绕过现有架构。
- 不做与当前任务无关的重构。
- 不要猜测问题，要实证排查：通过日志、断点、数据等实际证据定位原因，禁止凭猜测修改代码。
- 所有改动都必须可说明、可验证、可交付。

---

## 思考与实现原则
- 先理解业务目标、用户角色、核心流程，再进行设计和开发。
- 优先选择符合当前需求的最优可行方案，兼顾正确性、可维护性与实现成本。
- 尽可能复用现有代码、结构与组件；只有在明确存在复用价值时才新增抽象。
- 严禁过度设计、过度封装和无意义冗余，避免为单次需求引入不必要的层次和复杂度。
- 代码实现应保持清晰、简洁、稳定，优先保证业务正确性、可读性和后续维护性。
- 单个类、页面、组件、页面基类应保持职责单一，避免巨型文件和巨型类。发现文件持续膨胀、单类职责过多、阅读成本明显升高时，必须优先拆分为更小的组件、服务、辅助类或局部模块。禁止编写超大页面基类、超大工具类、超大 Service 类，禁止把多个无关职责长期堆在同一个类中。
- 遇到需求不清、规则冲突或实现复杂度明显升高时，先说明判断与权衡，再继续执行。

## 编码规则
- 所有源码、配置、文档文件统一使用 `UTF-8` 编码。
- 读取或修改含中文文件时，若出现乱码，先判断是终端显示问题还是文件编码损坏；未确认前禁止覆盖原文件。
- 禁止使用可能隐式改变编码的方式直接改写源码文件，如 shell 重定向、`Out-File`、`Set-Content`。
- Windows / PowerShell 下读取中文文件时，必须显式使用 `UTF-8`。
- PowerShell 命令不接受 `&&`，禁止使用；需要连续执行时改为分步执行或使用 PowerShell 兼容写法。
- 如果编写注释（含代码注释、文档注释等），统一使用中文，不使用纯英文注释；必要的英文标识、协议字段名或框架关键字可保留原文。
- 修改含中文内容后，必须重新读取一次并确认关键中文显示正常。

## 任务管理机制
`TASK.md` 与 `TaskHistory.md` 共同组成任务记录文件：`TASK.md` 只维护活跃任务与少量最近完成任务的最小记录，`TaskHistory.md` 用于归档历史 `DONE` 任务，两者均不负责承载规则解释。

### 任务状态
- `TODO`：未开始
- `DOING`：进行中
- `BLOCKED`：被阻塞
- `REVIEW`：已完成开发，等待确认
- `DONE`：已完成

### 执行规则
1. 开始工作前，先查看 `TASK.md` 是否已有对应任务。
2. 如果已有任务，优先更新原任务，不重复新建。
3. 如果没有任务，在 `TASK.md` 中新增最小任务记录。
4. 开始执行时，将任务状态更新为 `DOING`。
5. 若任务无法继续，更新为 `BLOCKED` 并写明原因。
6. 开发完成但仍需确认时，更新为 `REVIEW`。
7. 验证完成并确认交付后，更新为 `DONE`。
8. 当 `TASK.md` 中任务总数超过 30 条时，将最早完成的 `DONE` 任务迁移到 `TaskHistory.md`，直到 `TASK.md` 中任务数回落到 20 条以内。
9. 归档时仅允许迁移 `DONE` 任务，`TODO`、`DOING`、`BLOCKED`、`REVIEW` 任务必须保留在 `TASK.md`。
10. 归档任务时保留原任务 ID、任务信息与最近更新时间，并在 `TaskHistory.md` 中补充归档时间。
11. 发生任务归档时，在 `doc/devlog/` 中补充一份简短归档说明，记录迁移范围与触发原因。

### 每个任务至少包含
- 任务 ID
- 任务名称
- 任务目标
- 当前阶段
- 负责人 AI
- 任务状态
- 优先级
- 最近更新时间

### AI Agent 要求
- 开始任务前先同步任务状态。
- 开发过程中及时更新 `TASK.md`。
- 触发归档阈值时同步维护 `TaskHistory.md`。
- 范围变化时同步补充任务说明、验收标准和风险。
- 每次开发完成后，都需要在 `doc/devlog/` 下新增一份本次开发简短说明的 Markdown 记录。

## Git 与提交流程

### 分支命名
- `feat/<desc>`：新功能
- `fix/<desc>`：缺陷修复
- `refactor/<desc>`：无行为变更的重构
- `chore/<desc>`：工具、依赖、配置调整
- `docs/<desc>`：仅文档变更

### Commit 规范
- 提交信息优先采用 Conventional Commits
- 格式：`<type>(<scope>): <简短描述>`
- 示例：
  - `feat(next): add approval management board`
  - `fix(auth): correct session refresh logic`
  - `chore(prisma): add migration for audit log`

### 交付前自查
- 前端：`lint`、`typecheck`、`build`
- 服务端：关键服务测试、接口测试或等价验证
- 数据库：确认 Prisma schema 与 migration 已同步
- 环境变量：新增项已同步到 `.env.example`
- Docker：涉及构建链路时已完成镜像或容器验证

### 提交触发规则
- 每次修改完成后都应提交代码
- 若生成了本地运行产物、缓存、测试数据库、构建产物或依赖目录，应同步检查并更新 `.gitignore`

## 交付收口规范
- 当用户请求“开始开发”而非“只出方案”时，AI Agent 在实现完成后应默认继续做交付收口。
- 交付收口至少应按实际情况依次检查：
  1. 编译 / 测试
  2. 构建
  3. 发布构建与启动验证
  4. 应用级 smoke test
  5. 文档、`TASK.md`、`doc/devlog/`、忽略文件更新
- 若某项验证未执行，最终输出必须明确说明未执行项、原因、影响范围和建议下一步。

## 常见禁止事项
- 禁止在 Server Component 中请求自己的 `/api`
- 禁止在页面组件、hooks、store 中直接写 Prisma 查询
- 禁止在 Route Handler / Server Action 中堆积业务逻辑
- 禁止改了 `schema.prisma` 却不生成 migration
- 禁止在客户端代码中访问服务端密钥或数据库连接
- 禁止使用 inline style
- 禁止硬编码颜色值、间距值、圆角值、阴影值
- 禁止把服务端数据默认塞进 Zustand
- 禁止绕过 Zod 校验直接消费不可信输入
- 禁止引入未约定的新组件库、图标库、状态管理库
- 禁止交付缺少 `loading`、`empty`、`error`、`no-permission` 的页面
