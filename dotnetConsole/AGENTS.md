# AGENTS.md

## 目标
- `AGENTS.md`：只保留全局协作规范、阶段门控、任务机制、交付要求与子规则导航
- `application-AGENTS.md`：命令、Service、业务流程、配置、日志与测试
- `doc-AGENTS.md`：需求文档、`doc/devlog/` 与 `doc/task-archive/`
- `CLAUDE.md` / `GEMINI.md`：入口提示文件，只提醒先读 `AGENTS.md`
- `TASK.md`：唯一活动任务记录文件

---

## 快速命中卡片
- 只改规则、文档、需求说明：读 `doc-AGENTS.md`
- 改命令解析、Service、业务逻辑、日志、配置：读 `application-AGENTS.md`
- 命令行联调、构建或交付验证：先读当前文件，再按需回看命中的子规则
- 若只是很小的文案或规则修订，命中后只读对应子规则的相关段落，不必通读全文

---

## 最小充分上下文
- 简单问题、纯问答、方案判断：只加载回答当前问题所需的最小规则与文件，不默认预读全部子规则
- 单点低风险改动：先读当前文件，再读命中的一个子规则和目标文件；若信息已足够，不继续扩展上下文
- 只有在以下情况才继续补读更多规则或实现文件：
  - 需要实际落文件
  - 任务跨需求说明、命令实现与交付验证
  - 涉及配置、环境变量、启动方式或高风险命令重构
  - 当前信息不足以判断影响范围
- 若任务从简单问题升级为真实修改，应按命中场景逐步补充上下文，而不是一开始加载全部信息

## 根文件原则
- 根 `AGENTS.md` 只放所有任务都需要知道的规则，不重复展开实现与文档细节
- 只有任务命中对应场景时，才继续阅读对应子规则文件
- 用户指令始终高于本文件
- 先理解业务目标与现有实现，再修改代码或规则
- 优先复用现有结构，避免无关重构和过度设计
- 优先做可验证的改动；无法验证时必须说明原因、影响和建议下一步

## 开发阶段

### 三个阶段

```text
阶段 0          阶段 1              阶段 2
需求与说明  →   控制台实现       →   联调与交付
（用户确认）    （Codex）             （协作）
```

- 新功能默认按以上阶段推进，不满足入场条件不得跳阶段
- 可跳过阶段 0 的情况：
  - Bug 修复
  - 命令文案、帮助信息或轻量输出调整
  - 配置、日志格式或启动方式调整

### 阶段职责
- 阶段 0：需求整理、用法说明与文档维护，细则见 `doc-AGENTS.md`
- 阶段 1：命令解析、Service、配置、日志与测试，细则见 `application-AGENTS.md`
- 阶段 2：构建、运行、结果验证与交付收口，结合当前文件与命中的子规则执行

## 全局工作规则
- 先理解，再修改；不要基于猜测改代码
- 优先通过日志、输出结果、测试和运行验证等证据定位问题
- 先复用，再新增；不新增平行配置体系，不绕过现有架构
- 命令交付必须真实可运行，不能只停留在伪输出或示例层面
- 输出保持简洁，但分析、实现、验证要完整
- 已确认无变更风险的文件无需重复阅读；出现上下文缺口时必须补读
- 删除文件、删除目录、批量重构、环境清理等高风险操作，必须先获得明确确认

---

## 编码与文档规则
- 所有源码、配置、文档统一使用 `UTF-8`
- 读取或修改含中文文件时，如出现乱码，先判断是显示问题还是文件损坏，未确认前禁止覆盖
- Windows / PowerShell 下读取中文文件必须显式使用 `UTF-8`
- 禁止使用可能隐式改变编码的方式直接改写源码文件，如 shell 重定向、`Out-File`、`Set-Content`
- 修改含中文内容后，必须重新读取确认关键中文显示正常

## 任务管理
- `TASK.md` 是唯一活动任务记录文件，只维护最小任务记录与当前仍需关注的任务
- 开始工作前先检查是否已有任务；已有则更新原任务，没有则新增
- 任务状态仅使用：`TODO`、`DOING`、`BLOCKED`、`REVIEW`、`DONE`
- 开始执行时更新为 `DOING`
- 无法继续时更新为 `BLOCKED` 并写明原因
- 开发完成待确认时更新为 `REVIEW`
- 验证完成并确认交付后更新为 `DONE`
- 每条任务至少包含：任务 ID、任务名称、任务目标、当前阶段、负责人 AI、任务状态、优先级、最近更新时间

### 任务归档规则
- `TASK.md` 默认只保留：`TODO`、`DOING`、`BLOCKED`、`REVIEW`，以及最近少量 `DONE` 任务
- `TASK.md` 可按状态拆成“当前处理中”“待确认”“最近完成”“归档索引”等分区，优先保证活动任务易扫读
- 较早的 `DONE` 任务应按月归档到 `doc/task-archive/`
- `BLOCKED`、`REVIEW` 任务不得归档，避免仍需处理的事项从主表消失
- 触发归档的参考条件：
  - `TASK.md` 超过 20 条任务
  - `DONE` 任务超过 10 条
  - 完成一个阶段性里程碑或自然月切换
- 归档后，`TASK.md` 需保留归档索引，便于后续追溯

### 文档同步要求
- 每次开发完成后，都需要在 `doc/devlog/` 下新增一份简短开发记录
- 命令、脚本、环境变量、配置项与启动方式发生变化时，必须同步更新相关文档
- 需求文档与 devlog 细则见 `doc-AGENTS.md`

## Git 与交付

### Commit 规范
- 提交信息优先采用 Conventional Commits
- Commit 标题格式：`<type>(<scope>): <中文简述>`
- Commit 正文默认使用中文；非微小调整应补充以下字段：
  - `任务`
  - `阶段`
  - `原因`
  - `变更`
  - `验证`
  - `风险`
  - `关联`
  - `AI`
- 提交前确认 `TASK.md` 与 `doc/devlog/` 已同步；若未同步，需说明原因
- push、PR / MR、交付说明应优先复用最近一次 Commit 正文中的结构化字段，并使用中文摘要

### 提交前最小回归
- 文档或规则文件改动：重新读取改动文件，确认 `UTF-8` 与关键中文正常；无需强制执行 `lint` / `build`
- 命令、Service、配置或日志改动：至少执行项目现有的编译、静态检查或测试，并补一次真实命令运行、帮助信息验证或等价验证
- 启动方式、环境变量或输出协议改动：在应用回归基础上，再确认运行说明与相关文档已同步
- 若仓库当前缺少对应脚本，可使用“等价验证”替代，但必须在 Commit 正文和最终说明中写清执行内容与未覆盖风险

### 交付前自查
- 根据改动类型完成“提交前最小回归”
- 涉及构建链路时执行 `build`
- 至少验证一个核心命令路径或真实业务输出
- 文档、`TASK.md`、`doc/devlog/` 与忽略文件按需同步

### 交付收口
- 当用户请求“开始开发”而非“只出方案”时，实现完成后默认继续做交付收口
- 交付收口至少按实际情况检查：
  1. 编译 / 测试
  2. 构建
  3. 启动与结果验证
  4. 命令级 smoke test
  5. 文档、`TASK.md`、`doc/devlog/`、忽略文件更新
- 若某项验证未执行，必须明确说明未执行项、原因、影响范围和建议下一步

### 最终输出要求
- 最终输出优先使用中文，并至少说明：
  - 本次改了什么
  - 核心实现方式
  - 修改了哪些文件
  - 已执行和未执行的校验
  - 当前任务状态
  - 风险、阻塞或假设
  - 是否已更新 `doc/devlog/`

## 重复错误回顾机制
- 同一类问题连续出现两次错误时，必须做一次简短回顾
- 回顾至少说明：错误现象、根因、规则缺口、后续如何避免
- 回顾结论必须落实到当前架构目录的 `AGENTS.md` 或对应子规则文件中
- 回顾记录格式见 `doc-AGENTS.md`
- 若本次回顾导致规则变更，必须同步新增一条 `doc/devlog/` 记录
