# 文档规则

## 适用范围

- 作用域：设计文档、契约说明与开发文档维护
- 触发场景：涉及阶段 0 设计、契约说明、`doc/requirement.md` 时阅读

### 常见任务入口
- 新增功能方案：先看阶段 0 设计文档
- 更新字段、接口、DTO 或 schema：先看契约说明规范
- 更新通用说明：先看文档目录约定

---

## 主动建议规则
- 发现需求描述缺少角色、流程、字段、边界场景、验收标准或非功能要求时，应主动补充为待确认项
- 发现实现方案与需求文档、命令说明或设计文档不一致时，应主动提醒并建议同步修订
- 复用、查证优先级等共性规则见根 `AGENTS.md`「模型行为约束与主动建议」

## 阶段 0 设计文档

### 阶段 0 — 设计文档（新功能强制前置）

**触发条件**：用户提出新功能需求

**执行方式**：由用户与 AI 对话协作产出，用户最终确认定稿

**产物**：`doc/design/设计文档.md`（全项目一份，新功能以新章节追加，不新建文件）

**文档必须包含以下四个部分**：

| 部分 | 内容要求 |
| ---- | -------- |
| 架构设计 | 模块划分、命令结构、数据流向、涉及的技术决策说明 |
| 功能需求 | 命令列表、核心业务规则、关键状态说明 |
| 命令与输入输出 | 子命令、参数、选项、输出格式、退出码约定 |
| 处理流程 | 核心处理链路、状态流转、边界场景、异常处理方式 |

### 设计自检清单
设计文档不能只给抽象名词，必须能回答清楚以下 6 件事，否则视为方案没收敛：
- **入口**：谁调用、何时触发
- **核心流程**：按步骤写清楚，不是只给名词
- **状态变化**：输入、输出、中间状态如何演化
- **关键分支**：正常路径、异常路径、缺数据路径
- **副作用**：写文件、发请求、发通知、改配置、打日志
- **失败边界**：哪里应该 fail fast，哪里可以 warning 后继续

设计阶段禁忌：不为“以后可能会用”引入复杂扩展点；不堆兼容补丁式设计；不拿“通用最佳实践”压过仓库现状；不用“增加一个聚合层”“引入 orchestration 机制”这类抽象名词替代设计，必须说明它实际做什么。

**门控规则**：
- 用户明确确认设计文档后，才允许进入阶段 1。
- AI 在此阶段只输出文档内容，不写任何实现代码。

## 文档更新要求
以下内容发生变化时，必须同步更新相关文档：
- 命令、脚本或启动方式
- 环境变量
- 配置项
- 构建、发布或部署流程
- 数据库结构、迁移或初始化方式
- 对外使用方式或接口约定

优先更新已有文档，不新增重复说明。

### 文档目录约定
- `doc/requirement.md`：需求文档。若文件已存在，AI 应基于用户新增需求进行补充或修订；若文件不存在，AI 必须根据用户输入先自动生成详细初稿。该文件仅承载业务需求，不写入设计说明或开发过程记录
- `doc/design/设计文档.md`：项目设计文档，全项目一份。包含架构设计、功能需求、命令用法与输入输出示例（如适用）与交互说明。由用户与 AI 协作产出，用户确认后作为开发的唯一需求基准。AI 可在文件中追加新功能章节，不删除已有内容，不新建平行文件

### requirement 要求
- 若 `doc/requirement.md` 为模板初始状态，AI 应根据用户输入将占位内容替换为项目真实需求，而不是长期保留“待补充”空壳。
- 需求文档建议固定包含以下章节：项目背景、目标与范围、用户角色、命令或模块清单、核心业务流程、关键数据与字段、权限与可见范围、边界场景与异常、非功能要求、待确认项。
- 自动生成需求文档时，优先写清业务事实、流程与边界，不提前写入技术实现方案。

### 回顾分析记录格式
- 适用场景：同类错误连续出现两次后，触发简短回顾分析时使用
- 内容保持简短，建议至少包含：
  - 错误现象
  - 触发场景
  - 根因
  - 本次补充或修改的规则
  - 后续如何避免或验证不再复发
