# 文档规则

> 本规则的设计系统基于 Tailwind + shadcn 体系；含 **AI 产品交互补充**（Agent 输出展示、流式契约、用户确认节点、人工审核）。

## 适用范围

- 作用域：设计文档、契约说明、设计系统、AI 产品交互补充与开发文档维护
- 触发场景：涉及阶段 0 设计、契约说明、Agent 交互流程、`doc/requirement.md` 时阅读

### 阅读摘要
- 建议阅读：整理需求、补设计文档、维护契约、设计 Agent 交互流程、更新设计系统
- 可先跳过：纯界面实现、纯服务端逻辑、纯部署配置调整
- 优先查看：阶段 0 设计文档、AI 产品交互补充、契约说明规范、文档更新要求

### 常见任务入口
- 新增功能方案：先看阶段 0 设计文档
- 新增或改动 Agent 交互流程：先看 AI 产品交互补充
- 更新字段、接口、DTO、schema 或流式事件结构：先看契约说明规范
- 更新设计系统或通用说明：先看设计系统文件规范与文档目录约定

## 主动建议规则
- 发现需求描述缺少角色、流程、字段、权限、边界场景、验收标准、Agent 交互节点或非功能要求时，应主动补充为待确认项
- 发现实现方案与设计文档、接口契约、流式事件约定、需求基准或设计系统不一致时，应主动提醒并建议同步修订
- 维护文档时优先更新已有事实来源，不新增平行说明；确需新增文件时，应说明新增原因和归档位置
- 对不确定的业务事实、接口字段、模型行为和运行方式，只能标记为待确认或引用已验证来源，禁止写成确定结论

## 阶段 0 设计文档

### 阶段 0 — 设计文档（新功能强制前置）

**触发条件**：用户提出新功能需求

**执行方式**：由用户与 AI 对话协作产出，用户最终确认定稿

**产物**：`doc/design/设计文档.md`（全项目一份，新功能以新章节追加，不新建文件）

**文档必须包含以下部分**：

| 部分     | 内容要求                                                       |
| -------- | -------------------------------------------------------------- |
| 架构设计 | 模块划分、数据流向、涉及的技术决策说明（含 AI 层与 Agent 编排） |
| 功能需求 | 页面列表、功能点明细、业务规则、权限矩阵                       |
| 界面原型 | 每个页面的 ASCII 线框图，含关键状态（loading / streaming / empty / error） |
| 交互说明 | 操作流程、状态流转、边界场景、错误处理方式、Agent 交互节点     |
| AI 设计（如涉及） | 模型选择、Agent 职责、工具 / Skills 清单、Prompt 关键约束、可选能力是否引入 |

**门控规则**：
- 用户明确确认设计文档后，才允许进入阶段 1
- AI 在此阶段只输出文档内容，不写任何实现代码
- 涉及 AI 能力时，"AI 设计"部分需对照 `ai-AGENTS.md` 的核心 vs 可选清单，说明哪些是核心、哪些暂不引入

## AI 产品交互补充（本规则集增量）

Agent 产品的前端不能只是一个聊天框。设计 Agent 交互时，必须至少覆盖以下要点：

### 1. Agent 输出结构化展示
- 明确 Agent 会输出哪些结构化产物（候选列表、大纲、草稿、图表引用、步骤进度等）
- 每类产物对应一种展示组件（卡片 / 列表 / 步骤条 / 预览区），不能全塞进一段文本
- 线框图需画出每种产物的关键状态

### 2. 用户确认节点（Human-in-the-Loop）
- 标注哪些步骤需要用户确认 / 选择 / 编辑后才能继续
- 高风险动作（删除、外发、计费、不可逆操作）必须有人工确认，不得由 Agent 自动执行
- 确认节点在交互说明中显式画出，包含确认前 / 确认后 / 拒绝后的流转

### 3. 流式与进度反馈
- 标注哪些输出是流式的（打字机）、哪些是多步长任务（进度 / 阶段）
- 流式中断、超时、空响应的兜底展示
- 流式事件结构需与后端约定一致（见契约说明规范）

### 4. 状态完整性
- Agent 相关页面同样必须完整覆盖 loading / streaming / empty / error / no-permission
- 错误信息可读、可重试，不暴露模型 SDK 细节给用户

### 5. 边界与降级
- 模型不可用、限流、超长输入、空输出、工具调用失败时的降级路径
- 成本 / 延迟敏感场景的处理策略

## 接口契约规范

### 契约要求
- **唯一来源**：Swagger 自动生成（普通 REST 接口）
- **定义时机**：后端实现完成后，通过 Swagger UI 查看接口定义
- **变更规则**：接口变更时，必须先修改 DTO，再同步修改前端类型定义
- **文件结构建议**：前端按业务域拆分类型定义文件

### 流式 / Agent 契约补充
- 流式接口（SSE / 流式响应）的事件结构（事件类型、字段、终止信号）必须单独成文，作为前后端共同基准
- 流式事件字段变更时，按"先改契约 → 同步前后端 → 同步文档"顺序处理，不得前端私自解析
- Agent 中间产物（候选、草稿、步骤）的字段结构同样纳入契约管理

## 设计系统文件规范
`design-system.yaml` 是唯一设计系统文件，包含：
- 品牌与产品风格意图
- 语义化颜色 token（落地为 Tailwind 主题与 shadcn CSS 变量）
- 排版 token
- 间距、圆角、阴影 token
- 布局与断点规则
- shadcn / Tailwind 主题映射
- 页面状态规范（含 streaming）
- 组件使用规则
- 明确的 `do / dont` 规则

## 文档更新要求
以下内容发生变化时，必须同步更新相关文档：
- 命令、脚本或启动方式
- 环境变量（含模型密钥、Base URL、模型名）
- 配置项
- 构建、发布或部署流程
- 数据库结构、迁移或初始化方式、数据库切换（SQLite ↔ PostgreSQL）
- 模型对接方式、Agent 职责、工具 / Skills 清单、Prompt 关键约束
- 流式事件结构或对外接口约定

优先更新已有文档，不新增重复说明。

### 文档目录约定
- `doc/requirement.md`：需求文档。若文件已存在，AI 应基于用户新增需求进行补充或修订；若文件不存在，AI 必须根据用户输入先自动生成详细初稿。该文件仅承载业务需求，不写入设计说明或开发过程记录
- `doc/design/设计文档.md`：项目设计文档，全项目一份。包含架构设计、功能需求、界面原型（如适用）、交互说明与 AI 设计。由用户与 AI 协作产出，用户确认后作为开发的唯一需求基准。AI 可在文件中追加新功能章节，不删除已有内容，不新建平行文件

### requirement 要求
- 若 `doc/requirement.md` 为模板初始状态，AI 应根据用户输入将占位内容替换为项目真实需求，而不是长期保留"待补充"空壳。
- 需求文档建议固定包含以下章节：项目背景、目标与范围、用户角色、页面或模块清单、核心业务流程、关键数据与字段、权限与可见范围、边界场景与异常、非功能要求、待确认项。
- 自动生成需求文档时，优先写清业务事实、流程与边界，不提前写入技术实现方案。

### 回顾分析记录格式
- 适用场景：同类错误连续出现两次后，触发简短回顾分析时使用
- 内容保持简短，建议至少包含：
  - 错误现象
  - 触发场景
  - 根因
  - 本次补充或修改的规则
  - 后续如何避免或验证不再复发
