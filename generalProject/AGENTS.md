# AGENTS.md

## 目标
- `AGENTS.md`：只保留全局协作规范、阶段门控、任务机制、交付要求与子规则导航
- `frontend-AGENTS.md`：界面、视图、页面、组件、交互、样式与前端测试；没有前端或界面层时可跳过
- `backend-AGENTS.md`：接口、服务、业务逻辑、数据访问、鉴权、缓存、后端测试；没有独立服务端时按命中场景阅读
- `doc-AGENTS.md`：设计文档、契约说明、设计系统、`doc/devlog/`
- `infra-AGENTS.md`：环境变量、启动方式、构建发布、部署与交付验证
- `CLAUDE.md` / `GEMINI.md`：入口提示文件，只提醒先读 `AGENTS.md`
- `design-system.yaml`：设计 token 与 UI 规范
- `TASK.md`：唯一任务记录文件

---

## 快速命中卡片
- 只改规则、文档、设计说明：读 `doc-AGENTS.md`
- 改页面、视图、表单、样式、交互：读 `frontend-AGENTS.md`
- 改接口、服务、任务处理、数据访问、鉴权、缓存：读 `backend-AGENTS.md`
- 改环境变量、启动方式、打包、部署链路：读 `infra-AGENTS.md`
- 跨前后端联调或发布：至少同时读当前文件和命中的两个子规则
- 若只是很小的文案、样式或规则修订，命中后只读对应子规则的相关段落，不必通读全文

## 最小充分上下文

### 判断标准定义
- **简单问题**：可在5分钟内回答，无需代码修改的问题（如：解释概念、查询配置、查看现有实现）
- **单点低风险改动**：只涉及单一文件，修改内容少于20行，不影响接口契约、数据库结构、鉴权模型或部署链路
- **高风险内容**：涉及数据库迁移、权限变更、接口契约修改、环境变量变更、第三方集成、部署流程调整
- **无法继续（BLOCKED）**：遇到明确的技术障碍、依赖缺失、需要用户决策或外部资源
- **开发完成（REVIEW）**：代码实现完成，已通过自测，等待用户确认或代码审查

### 上下文加载规则
- 简单问题、纯问答、方案判断：只加载回答当前问题所需的最小规则与文件，不默认预读全部子规则
- 单点低风险改动：先读当前文件，再读命中的一个子规则和目标文件；若信息已足够，不继续扩展上下文
- 只有在以下情况才继续补读更多规则或实现文件：
  - 需要实际落文件
  - 任务跨前后端或跨多个领域
  - 涉及数据库、鉴权、发布、环境变量等高风险内容
  - 当前信息不足以判断影响范围
- 若任务从简单问题升级为真实修改，应按命中场景逐步补充上下文，而不是一开始加载全部信息

## 根文件原则
- 根 `AGENTS.md` 只放所有任务都需要知道的规则，不重复展开前端、后端、文档、基础设施细节
- 只有任务命中对应场景时，才继续阅读对应子规则文件
- 用户指令始终高于本文件
- 先理解业务目标与现有实现，再修改代码或规则
- 优先复用现有结构，避免无关重构和过度设计
- 优先做可验证的改动；无法验证时必须说明原因、影响和建议下一步

## 子规则索引

| 文件 | 适用范围 | 何时阅读 |
| --- | --- | --- |
| `frontend-AGENTS.md` | 界面、页面、视图、表单、交互、样式、前端 smoke test | 涉及任何用户界面或客户端交互时 |

### 按需阅读顺序
1. 先读当前文件，确认全局规则、任务阶段和交付要求。
2. 根据任务类型命中对应子规则，不预读全部文件。
3. 涉及界面时再读 `design-system.yaml`。
4. 再阅读相关模块与现有实现，确认复用点后再动手。

## 开发阶段

### 四个阶段

```text
阶段 0          阶段 1            阶段 2                阶段 3
设计文档   →   界面与功能实现   →   业务与数据实现   →   联调与交付
（用户确认）    （实现 AI）         （实现 AI）           （协作）
```

- 新功能需经过完整阶段流程，以下场景可简化或跳过阶段 0：
  - Bug 修复
  - 已有页面的样式或文案微调
  - 配置、环境变量、部署脚本调整
  - 单个字段增删改，且不引入新页面或新业务流程
- 除上述场景外，各阶段必须满足入场条件后方可进入下一阶段

### 阶段职责
- 阶段 0：需求整理、设计文档、契约说明，细则见 `doc-AGENTS.md`
- 阶段 1：界面骨架、交互、显示层契约，细则见 `frontend-AGENTS.md`
- 阶段 2：业务逻辑、数据持久化、鉴权与测试，细则见 `backend-AGENTS.md`
- 阶段 3：联调、构建、启动、部署与交付验证，结合当前文件与 `infra-AGENTS.md`

## 全局工作规则
- 先理解，再修改；不要基于猜测改代码
- 优先通过日志、数据、断点、测试等证据定位问题
- 先复用，再新增；不新增平行配置体系，不绕过现有架构
- 涉及新增、修改、删除等业务逻辑时，必须能真实生效并持久化；若当前阶段允许 mock，需在后续阶段补全真实链路
- 输出保持简洁，但分析、实现、验证要完整
- 已确认无变更风险的文件无需重复阅读；出现上下文缺口时必须补读
- 删除文件、删除目录、批量重构、数据库破坏性变更、环境清理等高风险操作，必须先获得明确确认

## 编码与文档规则
- 所有源码、配置、文档统一使用 `UTF-8`
- 读取或修改含中文文件时，如出现乱码，先判断是显示问题还是文件损坏，未确认前禁止覆盖
- Windows / PowerShell 下读取中文文件必须显式使用 `UTF-8`
- Windows / PowerShell 下处理中文 Git 提交信息时，优先使用 `git commit -m` / 多个 `-m` 参数，或使用 `UTF-8` 编码文件配合 `git commit -F <file>`
- 禁止通过标准输入管道直接传递中文提交信息，如 `git commit -F -`、here-string 管道等，避免编码链路把中文写成 `?`
- 禁止使用可能隐式改变编码的方式直接改写源码文件，如 shell 重定向、`Out-File`、`Set-Content`
- 修改含中文内容后，必须重新读取确认关键中文显示正常

## 任务管理
- `TASK.md` 是唯一活动任务记录文件，只维护最小任务记录与当前仍需关注的任务
- 开始工作前先检查是否已有任务；已有则更新原任务，没有则新增
- 任务状态仅使用：`TODO`、`DOING`、`BLOCKED`、`REVIEW`、`DONE`
- 开始执行时更新为 `DOING`
- 无法继续时更新为 `BLOCKED` 并写明原因
- 开发完成待确认时更新为 `REVIEW`
- 验证完成并确认交付后更新为 `DONE`
- 每条任务至少包含：任务 ID、任务名称、任务目标、当前阶段、负责人 AI、任务状态、优先级、最近更新时间

### 任务归档规则
- `TASK.md` 默认只保留：`TODO`、`DOING`、`BLOCKED`、`REVIEW`，以及最近少量 `DONE` 任务
- `TASK.md` 可按状态拆成“当前处理中”“待确认”“最近完成”“归档索引”等分区，优先保证活动任务易扫读
- 较早的 `DONE` 任务应按月归档到 `doc/task-archive/`
- `BLOCKED`、`REVIEW` 任务不得归档，避免仍需处理的事项从主表消失
- 触发归档的参考条件：
  - `TASK.md` 超过 20 条任务
  - `DONE` 任务超过 10 条
  - 完成一个阶段性里程碑或自然月切换
- 归档后，`TASK.md` 需保留归档索引，便于后续追溯

### 文档同步要求
- 每次开发完成后，都需要在 `doc/devlog/` 下新增一份简短开发记录
- 命令、脚本、环境变量、构建发布流程、数据库结构或对外接口约定发生变化时，必须同步更新相关文档
- 设计文档、契约说明、devlog 细则见 `doc-AGENTS.md`

## Git 与交付

### Commit 规范
- 提交信息优先采用 Conventional Commits
- Commit 标题格式：`<type>(<scope>): <中文简述>`
- Windows / PowerShell 下提交前，优先确保当前终端与 Git 日志输出使用 `UTF-8`；若刚执行过中文提交，需回读最近一次提交信息确认标题与正文未乱码
- Commit 正文默认使用中文；非微小调整应补充以下字段：
  - `任务`
  - `阶段`
  - `原因`
  - `变更`
  - `风险`
  - `关联`
  - `AI`
- Commit 正文中的 `风险` 仅记录真实的代码、业务、数据、兼容性、部署或发布风险，不写过程性说明
- 未执行人工测试、未补 smoke test、未覆盖某项校验、仅做等价验证等过程性说明，统一写在最终输出与 `doc/devlog/`，不写入 Commit 正文
- 提交前确认 `TASK.md` 与 `doc/devlog/` 已同步；若未同步，需说明原因
- push、PR / MR、交付说明应优先复用最近一次 Commit 正文中的结构化字段，并使用中文摘要

### 提交触发规则
- 当用户请求“开始开发”而非“只出方案”时，若本次代码、配置或规则改动已完成，且已完成本次改动所需验证，并已将 `TASK.md` 中对应任务状态更新为 `DONE`，则默认自动执行一次提交
- 自动提交前必须确认 `doc/devlog/` 已补充，且提交信息符合本节 `Commit 规范`
- 若验证尚未完成、任务状态尚未更新、仍存在明确阻塞，或用户明确要求暂不提交，则不得自动提交；需先说明原因与当前状态

### 提交前最小回归
- 文档或规则文件改动：重新读取改动文件，确认 `UTF-8` 与关键中文正常；无需强制执行 `lint` / `build`
- 界面或客户端改动：至少执行项目已有的静态检查，并补一项受影响页面、视图或组件的 smoke test / 交互验证
- 服务或业务逻辑改动：至少执行项目已有的静态检查，并补一项受影响服务、接口、任务或命令的测试 / 等价验证
- 数据、环境变量、部署链路改动：在对应场景回归基础上，再确认 schema / migration / `.env.example` / 启动验证 / 发布验证已同步
- 跨前后端或高风险改动：合并执行前后端最小回归，并至少补一次应用级 smoke test
- 若仓库当前缺少对应脚本或不同技术栈无统一命令，可使用“等价验证”替代，但必须在最终说明与 `doc/devlog/` 中写清执行内容、未覆盖校验和后续建议

### 交付前自查
- 根据改动类型完成“提交前最小回归”
- 界面层涉及构建链路时执行 `build` 或等价打包验证
- 业务逻辑涉及核心能力时补关键服务测试、接口测试或等价验证
- 数据库：确认 schema、migration、seed 与文档已同步
- 环境变量：新增项同步到 `.env.example`
- 部署链路：涉及构建、打包、发布时完成对应验证

### 交付收口
- 当用户请求“开始开发”而非“只出方案”时，实现完成后默认继续做交付收口
- 交付收口至少按实际情况检查：
  1. 编译 / 测试
  2. 构建
  3. 发布构建与启动验证
  4. 应用级 smoke test
  5. 文档、`TASK.md`、`doc/devlog/`、忽略文件更新
  6. 满足“提交触发规则”时完成自动提交
- 若某项验证未执行，必须明确说明未执行项、原因、影响范围和建议下一步

### 最终输出要求
- 最终输出优先使用中文，并至少说明：
  - 本次改了什么
  - 核心实现方式
  - 修改了哪些文件
  - 已执行和未执行的校验
  - 当前任务状态
  - 风险、阻塞或假设
  - 是否已更新 `doc/devlog/`

## 重复错误回顾机制
- 同一类问题连续出现两次错误时，必须做一次简短回顾
- 回顾至少说明：错误现象、根因、规则缺口、后续如何避免
- 回顾结论必须落实到当前架构目录的 `AGENTS.md` 或对应子规则文件中
- 回顾记录格式见 `doc-AGENTS.md`
- 若本次回顾导致规则变更，必须同步新增一条 `doc/devlog/` 记录
