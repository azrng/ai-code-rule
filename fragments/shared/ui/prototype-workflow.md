### 原型设计与确认

#### 启用门槛
- 命中任一条件必须先做原型，未确认前不得进入视图实现：
  - 新页面：新增独立页面、路由或窗口
  - 新模块：新增由多个页面 / 组件组成的功能模块
  - 交互改版：对既有页面做布局重构、导航调整或交互流程改版
- 命中任一条件可跳过原型专项，直接按设计文档实现：
  - Bug 修复：不改变界面结构与交互流程
  - 字段增删：仅在既有布局内增删展示或表单字段
  - 文案 / 样式微调：不改布局结构与交互逻辑的文字、颜色、间距等小改动
- 门槛判断有歧义（如改版幅度介于微调与交互改版之间）时，先向用户说明判断依据，由用户拍板是否启用

#### 技术选型决策表
| 场景 | 原型形态 | 说明 |
| --- | --- | --- |
| 普通 Web / 管理页面 | HTML 交互原型 | 单文件或少量静态 HTML，浏览器直接打开即可预览 |
| Flutter / Avalonia 等原生界面，涉及复杂手势、动画、拖拽或原生行为 | 最小可运行目标技术栈原型 | 用与正式开发一致的技术栈搭建可运行的最小工程验证交互 |
| 原生界面但交互简单 | 允许降级为 HTML 原型 | 仅有列表、表单、弹窗等常规交互时不必搭建原生工程 |

- 开工前 AI 必须先说明本次选型与理由（命中决策表哪一行、为什么），经用户确认后再开始做原型
- 用户对选型另有指定时以用户指定为准，并记录在设计文档中

#### 原型约束
- 红线一：原型一律使用模拟数据，禁止接入真实数据库、网络请求或业务逻辑
- 红线二：禁止过度开发——原型只覆盖确认视觉与交互所需的内容，不做性能优化、异常兜底、权限体系等工程化内容
- 覆盖范围至少包含：核心页面、页面间导航、关键交互流程、必要状态反馈（加载中、空数据、错误、无权限等）
- 原型中出现的视觉取值应基于 `design-system.yaml` 现状或拟调整值，便于确认后回填

#### 目录约定
- HTML 原型统一放 `doc/design/prototype/`（与文档目录约定一致），按 `<module>/<feature>.html` 命名并与功能设计文档互相链接，共享样式与静态资源放 `prototype/assets/`，页面以相对路径引用，不在每个页面内联重复
- 同栈最小可运行原型放独立工程目录（如 `doc/design/prototype/<module>/<feature>-proto/`），不混入正式工程结构，确认后按需迁移或删除

#### 用户确认门控
- 原型完成后先提交用户确认，明确列出覆盖的页面与交互范围
- 用户提出修改时先改原型再重新提交，直至用户明确确认
- 未经用户确认，不得开始视图实现；确认后的原型是后续视图实现的视觉与交互基线，正式开发应复用已确认原型的组件与取值
