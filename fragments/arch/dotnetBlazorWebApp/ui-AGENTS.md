# 界面规则

<!-- include: shared/ui/scope-web.md -->

### 常见任务入口
- 新增页面或交互：先看渲染模式选择，明确组件执行位置
- 改组件、状态或数据流：先看组件与状态规则与 JS interop 约束
- 改样式与视觉：先看设计系统，并遵循 `design-system.yaml`
- 补界面回归：先看 `提交前最小回归`

---

## 技术栈与适用范围

### Blazor Web App
- 面向 .NET Blazor Web App（版本以仓库现有 `TargetFramework` 为准，不主动升级，新项目先联网检索当前最新正式版），允许按组件或页面选择 Static SSR、Interactive Server、Interactive WebAssembly 或 Interactive Auto。
- 不得把 Blazor Web App 与传统 Blazor Server 托管模型混为一谈；旧模板、既有 SignalR Circuit 与服务器端组件状态规则继续使用 `dotnetBlazor` Profile。
- 使用 `AddRazorComponents()` 注册 Razor Components，并仅为实际使用的交互模式追加对应服务与端点配置。
- 如果仓库已有真实实现，以现有代码和目标框架支持的官方能力为准，不为统一模板强制迁移渲染模式。

### 设计系统
<!-- include: shared/ui/design-system-liveness.md -->
- 使用 BootstrapBlazor 主题系统，所有视觉规范在 `design-system.yaml` 中定义。
- 优先复用现有组件、样式和设计 token，禁止 inline style，禁止硬编码颜色、间距或圆角。

## 渲染模式选择

### Static SSR
- 组件只在服务器处理请求时执行并输出 HTML，不建立交互式组件运行时。
- 适用于只读内容、内容详情、登录前页面、搜索引擎可索引页面，以及以普通导航和表单提交完成交互的场景。
- 不需要客户端事件处理时优先使用 Static SSR，不应仅为局部简单交互把整个应用设为交互式。
- Static SSR 请求之间不保留组件实例和内存状态；跨请求状态必须放入显式持久化位置，并按用户和权限隔离。
- Static SSR 阶段不得依赖浏览器 DOM、客户端存储或 JS interop 已可用。

### Interactive Server
- 组件在服务器执行，浏览器通过 SignalR Circuit 传递 UI 事件和渲染差异。
- 适用于需要完整 .NET 服务端能力、服务端资源访问、较小客户端下载量和快速首次交互的场景。
- 每个连接会占用服务器内存与连接资源；容量规划必须覆盖并发 Circuit、断线保留时间、负载均衡和部署滚动更新。
- 组件状态属于当前 Circuit，不得把内存中的组件状态当作可靠持久化状态；关键操作必须具备幂等或可恢复设计。
- 不得向 UI 暴露服务器密钥、连接串或仅因代码在服务器执行就绕过授权检查。

### Interactive WebAssembly
- 组件及其可达代码在浏览器 WebAssembly 运行，服务端只提供静态资源、SSR 输出和 API 等能力。
- 适用于需要离线倾向、降低持续服务器连接压力、客户端就近交互，且功能可以通过受保护 API 获取数据的场景。
- 客户端程序集、配置、网络请求和运行时状态均可被用户检查，不得包含密钥、私有连接串、可信授权决策或只能在服务器执行的业务规则。
- 浏览器端无法直接使用仅在服务器注册的服务；共享抽象必须分别提供客户端实现和服务器实现，涉及数据访问时通过明确 API 或其他受保护边界调用。
- 必须评估首次下载体积、缓存更新、弱网体验和浏览器能力，不得默认所有页面都适合 WebAssembly。

### Interactive Auto
- 首次访问通常先以 Interactive Server 提供交互，客户端资源下载并缓存后，后续访问可在 WebAssembly 执行。
- 仅适用于同一组件能够在服务器和浏览器两侧正确运行、依赖均有双端实现、行为在两种执行位置一致的场景。
- 业务代码不得假设固定执行位置；需要区分运行环境时应把差异封装在明确的服务边界内。
- 不得依赖 Auto 模式作为即时负载切换或当前 Circuit 断线后的透明迁移机制。

### 选择原则
- 先按页面和组件实际需求选择最小能力模式，再考虑扩大作用域。
- 同一页面混用模式前必须明确组件边界、参数传递、认证状态、服务可用性和预渲染行为。
- 渲染模式属于架构契约。新增或调整模式时，应同步更新设计文档、测试、部署容量假设和故障恢复说明。

## 执行位置、DI 与数据边界

- 每个组件必须明确代码实际执行在服务器、浏览器，还是可能在两端执行。
- Interactive Server 的 scoped 服务通常随 Circuit 存活；不得把它误认为单次 HTTP 请求作用域，也不得在 Singleton 中持有用户 Circuit 状态。
- Interactive WebAssembly 的 scoped 服务在客户端应用生命周期内表现为客户端作用域；不得据此承载服务器可信状态。
- Auto 或可双端执行的组件只可注入双方均能解析的抽象。服务器专属依赖应留在服务器边界，客户端通过受保护接口访问。
- 从服务器边界传向交互式客户端的参数和持久化状态必须可序列化，使用稳定、最小化的数据契约，不传递服务实例、委托、数据库实体跟踪对象或其他服务器对象图。
- 组件参数、持久化组件状态和 API 响应均是不可信边界。服务端必须重新验证输入、身份、权限、资源归属和业务约束。
- 授权决策必须在执行敏感操作的服务器端重复实施；`AuthorizeView`、隐藏按钮和客户端路由保护只用于界面呈现，不能替代服务端授权。
- 错误信息返回客户端前必须去除堆栈、连接信息、密钥和内部实现细节。

## 预渲染与生命周期

- 交互式组件默认可能先在服务器预渲染，再建立 Interactive Server Circuit 或启动 WebAssembly 运行时。
- 预渲染和交互启动可能导致生命周期逻辑执行两次。数据加载、日志、遥测和外部副作用必须可识别重复执行，写操作必须幂等。
- 需要跨预渲染与交互阶段复用的数据时，使用框架支持的持久化组件状态机制，并限制为当前页面真正需要的最小可序列化数据。
- 预渲染期间浏览器 DOM 和 JS 运行时尚不可用。JS interop、尺寸测量、焦点和客户端存储访问必须延后到组件完成交互式渲染后执行。
- 只有在预渲染无法安全支持且用户体验收益明确时才关闭预渲染，并记录首屏、闪烁、SEO 和加载状态影响。
- 组件必须为预渲染、交互启动、数据未到达和恢复失败提供确定的 loading、empty、error 与 no-permission 状态。

## 断线、恢复与状态

### Interactive Server
- 将断线视为正常运行状态，提供可理解的重连提示、等待状态和失败后的安全刷新或重新进入路径。
- Circuit 可能因网络、服务器重启、部署、超时或容量回收而永久丢失。关键草稿和业务进度不得只保存在组件字段或 scoped 内存服务中。
- 重连后可能再次触发用户操作或数据加载。命令、提交和支付类操作必须使用业务幂等键、并发控制或服务端去重。
- 不得假设恢复后 DOM、JS 对象引用、组件实例或服务器内存状态仍然有效。

### Interactive WebAssembly 与 Auto
- 网络失败时区分本地 UI 状态、待同步操作和服务端已确认结果，不用模糊的成功提示掩盖未提交状态。
- 需要离线或延迟同步时必须显式设计缓存版本、冲突解决、重试上限和用户可见状态，不得把浏览器存储当作可靠服务端提交。
- Auto 模式必须验证服务器执行和 WebAssembly 执行下的状态恢复、认证过期、缓存版本与接口兼容性。

## JS interop 约束
- 优先使用 Razor 和 .NET 组件能力，仅在浏览器 API、第三方 JavaScript 库或 DOM 能力不可替代时使用 JS interop。
- 预渲染期间禁止调用依赖浏览器的 JS interop；通常在交互式 `OnAfterRenderAsync` 阶段并结合首次渲染判断执行初始化。
- 不在组件渲染过程中直接修改由 Blazor 管理的 DOM；第三方库必须限制在明确拥有的容器内，并提供初始化、更新和释放流程。
- `IJSObjectReference`、DOM 引用和客户端模块引用均有生命周期，组件释放时应尽力释放，并容忍 Circuit 已断开或浏览器上下文已失效。
- Interactive Server 的 JS interop 是跨网络调用，参数与返回值需可序列化；避免高频细粒度调用，优先批处理，并处理超时、取消和断线异常。
- Interactive WebAssembly 也不得把 JS 返回值视为可信输入；涉及权限或持久化的数据必须由服务器重新校验。
- 不把密钥、访问令牌或敏感数据写入 DOM、日志、查询串或长期浏览器存储。确需客户端令牌时，遵循项目既有认证方案和最小权限原则。

## 组件与状态规则

- 优先复用 `Components/` 下已有组件，只在有明确复用价值时新增共享组件。
- 组件参数保持简单、可序列化和稳定，跨渲染模式边界时避免传递渲染片段、委托或服务器对象。
- 服务层封装业务逻辑，组件只负责展示、输入协调和调用编排。
- 共享状态必须标注所属位置和生命周期：单次请求、Circuit、浏览器应用、持久化服务端或跨设备状态。
- 修改共享状态必须通过服务方法，禁止从多个组件直接修改同一可变对象。
- 异步操作使用 `async Task`，传递取消信号，组件释放后不得继续更新 UI。
- 页面状态必须覆盖 loading、empty、error、no-permission、disconnected，以及需要时的 offline 或 pending-sync。

## 测试与验证

<!-- include: shared/ui/pre-commit-regression-web.md -->

- 影响行为的改动应优先补充或更新测试；未补测试时必须说明原因和风险。
- 使用 bUnit 或项目既有组件测试方案验证参数、渲染输出、事件和关键状态。
- Static SSR 至少验证首个请求 HTML、普通导航或表单行为，以及无交互运行时条件下的可用性。
- Interactive Server 至少验证 Circuit 建立、断线提示、重连失败路径、幂等提交和服务器端授权。
- Interactive WebAssembly 至少验证客户端下载、API 失败、认证过期、无服务器专属 DI 依赖和客户端不含秘密。
- Interactive Auto 必须分别验证首次服务器交互和缓存后 WebAssembly 执行，不能只测试其中一种路径。
- 启用预渲染时验证重复生命周期不会产生重复写入，并验证交互启动前不会执行浏览器专属 JS interop。
- 关键页面执行 smoke test，确认页面可访问、主要交互可触发、核心状态和渲染模式符合设计。
