# 基础设施规则

## 适用范围

- 作用域：打包与发布链路、CI 工作流、环境变量、版本号交付与验证规则
- 本形态没有容器化部署链路：交付物是包源上的 NuGet 包（与文档站，如有），不涉及 Docker、端口映射或常驻服务运行
- 触发场景：涉及打包、发布、版本号、CI、环境变量或交付链路时阅读

### 常见任务入口
- 改打包脚本或 CI 工作流：先看「发布链路」与「提交前最小回归」
- 改环境变量、连接串或测试配置：先看「环境变量」
- 改包公开 API、版本号或 README：先看「发布纪律」与「提交前最小回归」

---

## 技术选择原则
如果仓库已经有真实实现，以现有代码为准，不要强行重构或替换技术栈。
技术债务与重构判断遵循 `collaboration-AGENTS.md` 的「纠错、回退与重构」。

---

## 发布链路

### CI 发布（主链路）
- 触发：push 到主分支 → CI 发布工作流，对打包解决方案执行 `dotnet restore / build / pack --configuration Release` 后推送包源
- 推送凭据优先 OIDC Trusted Publishing / 短时密钥；使用长期 API 密钥时只放受保护 Secret，禁止明文进仓库或 workflow
- 新包要走 CI 发布，必须已登记进打包解决方案（登记口径见 `backend-AGENTS.md`「包仓库组织」）
- 修改发布链路（打包解决方案成员、workflow、脚本）时，必须能说明发布产物来源与推送目标，不允许出现「打包了但没人推」或「推了但版本来源不明」的断链

### 本地批量打包（备用链路）
- 本地打包脚本仅作备用 / 自测：输出独立目录、逐包推送、单个失败继续；与 CI 的差异（配置、凭据、解决方案范围）要能说清
- 发布正式版本优先走 CI，保证产物来源可追踪

### 文档站（如有）
- 文档站由 XML 文档构建产物生成时，包工程保持 XML 文档生成开启（`GenerateDocumentationFile`），文档口径见 `doc-AGENTS.md`
- 文档站工作流触发范围（源码路径 / 生成器目录）变更时，同步核对触达条件

---

## 发布纪律（NuGet 包）

- 破坏性变更必须升 major 版本号，不得借 minor / patch 号发布；破坏性判定见 `backend-AGENTS.md`「包公开 API 契约」
- 已按某版本开发的内容，发布前不得回退版本号「降级」发出；确需调整版本号时，必须同步核对 README 安装示例、版本更新记录与实际 API 形态是否一致
- 发布前核对三处一致：csproj `<Version>`、README 安装示例 `--version`、README / CHANGELOG 版本记录的最新版本号
- 包源不可覆盖：发布后发现内容失实，只能在下一版本修正，并在版本更新记录中说明误发情况

## 环境变量

- 仓库无统一 `.env` 体系时：测试与工具按需读取进程环境变量，命名沿用仓库现有前缀约定；新增环境变量在读取它的测试项目内注释或对应包 README 中说明用途、取值来源与缺省行为（通常未设置即跳过对应用例）
- 禁止把连接串、密钥、API Key 写入仓库文件；本地脚本专用密钥只经环境变量注入，禁止提交

---

## 主动建议规则
- 发现打包脚本、CI 工作流、版本号或包文档之间存在不一致、不可复现或文档缺失时，应主动提醒
- 发现可以复用既有打包 / 发布脚本与工作流时，应优先建议复用，不新增平行发布链路
- 不确定包源地址、密钥来源或包版本号时，应按根 `AGENTS.md` 的查证优先级处理，禁止凭经验写死配置
- 涉及清理环境、删除数据、停止未知进程、修改发布配置等高风险操作时，只能提出建议，必须等待明确确认后执行

## 阶段 2 — 打包与交付验证

**触发条件**：用户发出「开始验证」「开始交付」或等价指令；未明确发出时，阶段 1 门控全部满足后按 `collaboration-AGENTS.md`「Git、验证与交付」继续收口

**入场要求**：阶段 1 门控已全部满足；发现的契约缺口均已按 `collaboration-AGENTS.md`「纠错、回退与重构」处理完毕

**工作内容**：
1. 按改动类型执行本文件与 `backend-AGENTS.md` 的「提交前最小回归」对应项。
2. 打包验证：受影响包 `dotnet pack`（独立输出目录）可生成产物，产物内的版本号与依赖清单符合预期。
3. 按 `collaboration-AGENTS.md`「Git、验证与交付」汇总交付说明：已执行与未执行的校验、风险与待确认项。

**门控规则**：
- 受影响包的测试与打包验证通过；未执行的验证项已说明原因、影响范围和建议下一步。
- 版本三处一致已核对；文档与 `TASK.md` 已同步。
- 按 `collaboration-AGENTS.md`「Git、验证与交付」执行提交口径：验证通过后默认提交本任务改动且不自动推送，用户明确要求暂缓或禁止提交时不提交。

---

## 提交前最小回归
- 修改 workflow、打包脚本或打包解决方案成员时：核对触发分支与推送目标语法正确，并至少执行一次受影响包的 `dotnet pack`（独立输出目录，见 `backend-AGENTS.md`「.NET 并行隔离」）等价验证产物可生成
- 修改包公开 API、版本号或 README 时：执行 `dotnet pack`（独立输出目录）确认产物可生成，并核对版本三处一致（见「发布纪律」）
- 修改环境变量、配置项或连接串时：确认读取处的测试缺省行为（未设置即跳过）与文档说明同步更新
- 修改数据库、仓储、依赖注入或外部服务集成时：至少补一项真实链路或等价验证
- CI 工作流无法本地完整复现（OIDC、包源凭据）时，说明未覆盖项，用 workflow_dispatch 或推送到验证分支的方式补验
