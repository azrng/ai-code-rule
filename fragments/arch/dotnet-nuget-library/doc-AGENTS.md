# 文档规则

## 适用范围

- 作用域：包公开 API 契约说明、包级 README / CHANGELOG / ARCHITECTURE、仓库级开发日志与方案记录维护
- 触发场景：涉及契约说明、包 README / CHANGELOG / ARCHITECTURE、方案记录或开发日志时阅读

### 常见任务入口
- 改公开 API（接口、DTO、Options、扩展方法）：先看「接口契约规范」
- 更新包使用说明或版本记录：先看「包文档结构与版本记录」
- 新增方案 / 迁移记录或开发日志：先看「文档目录约定」

---

## 主动建议规则
- 发现实现、公开 API 契约与 README / ARCHITECTURE 描述不一致时，应主动提醒并建议同步修订
- 维护文档时优先更新已有事实来源，不新增平行说明；确需新增文件时，应说明新增原因和归档位置
- 对不确定的业务事实、接口字段和运行方式，只能标记为待确认或引用已验证来源，禁止写成确定结论
- 涉及运行时、框架或依赖版本的文档表述，写具体版本号与核实日期（按官方支持策略核实）；禁止「当前 LTS」「最新版」这类会过期的表述

---

## 接口契约规范

### 契约要求

- **唯一来源**：包的公开 API（公开接口、DTO、Options、扩展方法签名）与示例宿主的 Controller / DTO 公开定义；破坏性变更口径见 `backend-AGENTS.md`「包公开 API 契约」与 `infra-AGENTS.md`「发布纪律」。
- **验证方式**：包以测试工程 / 示例宿主的真实调用与 XML 注释为准；宿主 Web API 通过 Swagger UI 展示和验证契约，不把 Swagger 文档本身当作手工维护源。
- **变更规则**：契约变更时，必须先修改公开接口 / DTO 定义，再同步实现、测试、示例与 README / CHANGELOG 版本记录。
- **回退规则**：实现过程发现契约缺口时，按 `collaboration-AGENTS.md` 的「纠错、回退与重构」回到契约变更流程，不在实现层绕过契约或临时补字段。
- **文件结构建议**：按业务域拆分 DTO 与契约文件，避免将全部请求和响应堆叠在单个文件中。

## 包文档结构与版本记录

### 包目录文档
- 每个包目录维护 `README.md`：项目定位、安装方式（含 `--version` 的安装命令）、主要用法、当前版本的简要变更
- 版本历史持续增长、明显影响使用说明阅读时，将历史记录迁移到同目录 `CHANGELOG.md`；迁移保留原有条目，不因文档拆分改写发布事实
- `CHANGELOG.md` 按版本号倒序维护，每个版本独立成节；README 只保留当前版本简要变更并指向 CHANGELOG
- 包内部设计、数据流与技术决策放同目录 `ARCHITECTURE.md`（按需）；文档与代码冲突时代码为事实来源，文档随后修正
- README 指向变更记录的链接使用绝对仓库 HTTPS 地址，确保包源页面渲染后可以直接访问仓库中的 `CHANGELOG.md`

### 版本一致性
- 发布或升版前核对三处一致：csproj `<Version>`、README 安装示例 `--version`、README / CHANGELOG 版本记录的最新版本号；不一致先改齐再进入发布
- csproj 元数据口径：`<PackageReadmeFile>` 指向 `README.md`；`PackageProjectUrl` 指向项目文档入口，`RepositoryUrl` 指向代码仓库，不用变更记录替代包首页说明或项目主页

## 文档更新要求
以下内容发生变化时，必须同步更新相关文档：
- 命令、脚本或启动方式
- 环境变量
- 配置项
- 构建、打包或发布流程
- 数据库结构、迁移或初始化方式
- 对外使用方式或接口约定（含 NuGet 包公开 API 与 README / CHANGELOG 版本记录）

文档同步是命中上述清单的任务的完成前置条件：置 `DONE` 前先比对本次改动，命中则在同一任务内更新文档，不得跨任务事后补录。优先更新已有文档，不新增重复说明。

### 包仓库契约口径
- 本形态不维护 `CON-` 契约草案库：包公开 API 是唯一事实来源（见「接口契约规范」），阶段 0 的 API 设计要点记入包目录 `ARCHITECTURE.md` 或 `doc/` 主题方案文件，不另建契约编号体系

### 文档目录约定
- 包对外契约与用法以包目录 README 为入口，内部设计以 ARCHITECTURE 为准；仓库级文档（开发日志、评审记录、大型方案 / 迁移计划）集中在仓库文档目录按主题维护，不另建平行目录体系
- 为较大功能写方案 / 迁移计划时，按主题命名新增文件，写清背景、方案、边界与验证方式即可，不强制模板和编号体系
- 开发日志只记录当次任务事实（改动、验证、结论），不重复维护与 README / ARCHITECTURE 冲突的长期说明
