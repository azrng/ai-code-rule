# 后端规则

## 适用范围

- 作用域：接口、服务、业务逻辑、任务处理、数据访问、缓存、鉴权、异常处理与后端测试
- 触发场景：涉及服务逻辑、数据库、缓存、权限、消息队列、定时任务、第三方集成时阅读

### 常见任务入口
- 改接口响应或状态码：先看 `接口规则`、`异常处理规范`
- 改业务逻辑或状态切换：先看 `应用服务 / 领域服务规则`
- 改查询、分页、事务、数据库：先看 `数据访问规则`、`提交前最小回归`
- 改鉴权与外部集成：先看 `鉴权与权限规则`、`第三方集成规范`

---

## 技术栈

### 通用原则
- 不预设具体编程语言、Web 框架、ORM、数据库、中间件或消息系统
- 接口风格可为 REST、RPC、命令式任务入口或框架原生机制，但必须保持项目内统一
- 入参、出参、领域对象、错误对象应有明确类型、schema 或结构约束

## 主动建议规则
- 发现业务逻辑放错层、入口层与服务层职责混杂、权限校验缺失、事务边界不清或异常处理不一致时，应主动提醒
- 发现接口契约、schema / DTO / 类型定义、存储结构、缓存策略或状态流转可能影响历史数据、兼容性或权限安全时，必须先说明风险，不得直接扩大修改
- 发现可以复用既有服务、数据访问封装、schema / DTO / 类型定义、校验器、错误处理封装或第三方集成封装时，应优先建议复用
- 不确定业务规则、权限规则、数据含义或外部接口行为时，应按根 `AGENTS.md` 的查证优先级处理，禁止按通用经验补写规则

## 阶段 2 — 服务端与数据实现

**触发条件**：用户发出“开始后端开发”或等价指令

**入场要求**：页面结构已完成，schema 与契约清晰

**工作内容**：
1. 按项目现有分层实现业务能力，如接口层 -> 服务层 -> 数据访问层，或项目现有等价结构。
2. 根据需求维护 schema、迁移脚本、初始化数据、数据约束与索引。
3. 完成认证、鉴权、日志、缓存、分页、筛选、排序、定时任务或消息处理等逻辑。
4. 每个核心能力都必须可通过页面、接口工具、脚本、命令或测试独立验证。

**门控规则**：
- 核心服务与接口独立验证通过后，才允许进入阶段 3。
- 后续实现发现契约缺口时，按 `collaboration-AGENTS.md`「纠错、回退与重构」回到 schema / DTO / 类型定义变更流程，不在实现层绕过契约。

## 服务端规则

### 分层依赖规则
```text
入口层 / 接口层 / 任务入口
        ↓
业务服务 / 应用服务 / 领域服务
        ↓
数据访问层 / 外部集成层
        ↓
数据库 / 缓存 / 消息系统 / 第三方服务
```

### 接口规则
- 入口层只负责协议解析、鉴权、参数校验、状态码和响应结构
- 不直接承载复杂业务逻辑或复杂数据查询
- 对外返回明确、稳定、可解析的响应结构
- 对外开放接口要显式处理项目中约定的错误分类和状态表达方式

### 应用服务 / 领域服务规则
- 服务方法命名使用业务语义，如 `createOrder`、`approveRequest`
- 业务校验、权限判断、去重判断、状态流转、事务边界放在服务层
- 返回明确的类型结果，不返回未约束的 `any`
- 对外部系统调用进行必要的超时、失败与重试控制

### 数据访问规则
- ORM、SQL、查询构造器、仓储层或文件存储访问统一收敛在项目约定目录中
- 数据查询不得散落在页面组件、浏览器端代码、控制器或任务入口层中
- 复杂查询、分页、排序、条件拼装收敛到数据访问层
- schema 或存储结构变更后必须同步 migration、初始化数据、类型与文档
- 读写一致性、事务边界和并发冲突必须明确处理

### 鉴权与权限规则
- 粗粒度访问控制可放在中间件、路由守卫、过滤器或入口拦截层
- 细粒度业务权限必须在服务层再次校验
- 会话、Cookie、Token、用户身份解析统一在服务端处理
- 客户端只能消费鉴权结果，不负责任何安全边界的最终判定

### 缓存与一致性规则
- 使用缓存时必须说明缓存目标、失效条件和一致性策略
- 写操作后必须刷新或失效受影响缓存
- 对权限相关、实时性强或强一致场景默认谨慎缓存
- 不允许“提交成功但读取仍是旧数据”的伪完成状态

### 异常处理规范
- 自定义业务异常统一收敛到项目约定位置
- 区分校验错误、权限错误、资源不存在、状态冲突、系统异常
- 入口层负责把业务异常转换为稳定响应
- 禁止把原始数据库异常、堆栈或敏感信息直接透传给前端

### 第三方集成规范
- 邮件、短信、对象存储、Webhook、支付、消息队列等能力统一放在集成层
- 第三方密钥只允许从服务端环境变量读取
- 所有第三方调用都必须具备错误处理、日志和必要的重试策略

### 代码组织规范
- 一个文件只放一个主对象：路由处理、Service、Repository、数据模型、配置类各自独立文件，文件名与主对象一致。
- 数据契约（请求 / 响应 / DTO）按业务域分文件定义，不合并到一个大杂烩文件。
- 触发拆分的信号：单文件出现多个主对象、函数或字段持续堆叠、模块跨多个不相关业务。
- 允许例外：紧耦合的常量、接口分组、测试 fixture。
- 反模式：一个文件堆放所有数据模型或所有请求 / 响应定义；把多个不相关 Service 塞进同一文件。
