# 文档规则

## 适用范围

- 作用域：设计文档、契约说明、设计系统与开发文档维护
- 触发场景：涉及阶段 0 设计、契约说明、`design-system.yaml`、`doc/requirement.md` 时阅读

### 常见任务入口
- 新增功能方案：先看阶段 0 设计文档
- 更新 IPC method、DTO、schema 或事件载荷：先看契约说明规范
- 更新设计系统或通用说明：先看设计系统文件规范与文档目录约定

---

## 主动建议规则
- 发现需求描述缺少角色、流程、字段、权限、边界场景、验收标准或非功能要求时，应主动补充为待确认项
- 发现实现方案与设计文档、接口契约、需求基准或设计系统不一致时，应主动提醒并建议同步修订
- 复用、查证优先级等共性规则见根 `AGENTS.md`「模型行为约束与主动建议」

---

## 阶段 0 设计文档

### 阶段 0 — 设计文档（新功能强制前置）

**触发条件**：用户提出新功能需求

**执行方式**：由用户与 AI 协作产出，用户最终确认定稿

**产物**：`doc/design/设计文档.md`（全项目一份，新功能以新增章节方式补充）

**文档必须包含以下四个部分**：

| 部分 | 内容要求 |
| --- | --- |
| 架构设计 | 模块划分、Electron / .NET / 前端边界、数据流向、缓存与权限方案 |
| 功能需求 | 页面清单、功能点明细、业务规则、权限矩阵 |
| 界面原型 | 每个页面的 ASCII 线框图，包含 `loading` / `empty` / `error` / `no-permission` 状态 |
| 交互说明 | 操作流程、状态流转、边界场景、错误提示与恢复方式 |

### 设计自检清单
设计文档不能只给抽象名词，必须能回答清楚以下 6 件事，否则视为方案没收敛：
- **入口**：谁调用、何时触发
- **核心流程**：按步骤写清楚，不是只给名词
- **状态变化**：输入、输出、中间状态如何演化
- **关键分支**：正常路径、异常路径、缺数据路径
- **副作用**：写文件、发请求、发通知、改配置、打日志
- **失败边界**：哪里应该 fail fast，哪里可以 warning 后继续

设计阶段禁忌：不为“以后可能会用”引入复杂扩展点；不堆兼容补丁式设计；不拿“通用最佳实践”压过仓库现状；不用“增加一个聚合层”“引入 orchestration 机制”这类抽象名词替代设计，必须说明它实际做什么。

**门控规则**：
- 用户明确确认设计文档后，才允许进入阶段 1
- AI 在此阶段只输出文档内容，不编写实现代码

## 契约说明规范

### 契约要求

- **前端唯一事实来源**：`schemas/` 中的 Zod schema 与共享类型定义
- **.NET 边界事实来源**：`src-dotnet/` 中的 DTO / IPC 入参出参定义
- **定义方式**：表单 schema、Query schema、IPC 入参 schema、IPC 出参结构必须成对维护
- **变更规则**：字段或行为变化时，必须同步更新 schema、类型、页面、IPC 封装与测试
- **生成式契约**：若 sidecar 以路由表和 DTO 声明 method，应以其为跨语言契约事实来源，在构建期生成 TypeScript method 常量、类型和基础 SDK；生成文件不作为手工维护入口。
- **流式契约**：流式 method 要记录最终响应、进度 notification、requestId 关联键、取消 method、总时长、空闲时长与审批等待期间的计时策略。
- **调用选择原则**：
  - 桌面应用内部业务交互：优先 IPC handler（stdio JSON-RPC）
  - 事件通知或后台状态推送：使用 Electron 主进程向渲染进程的推送
  - 外部服务访问：使用前端统一请求层或 .NET 侧 `Integrations/`，不新增本地 HTTP 桥接

## 设计系统文件规范

`design-system.yaml` 是唯一设计系统文件，包含：
- 品牌与产品风格意图
- 颜色、排版、间距、圆角、阴影等 token
- 布局与断点规则
- 页面状态规范
- 表单与反馈组件规则
- 明确的 `do / dont`

## 文档更新要求

以下内容发生变化时，必须同步更新相关文档：
- 命令、脚本或启动方式
- 环境变量
- 配置项
- 构建、发布、签名或更新流程
- 本地数据库结构、迁移或初始化方式
- 对外使用方式或接口约定

优先更新已有文档，不新增重复说明。

### 文档目录约定
- `doc/requirement.md`：需求文档。若文件已存在，AI 应基于用户新增需求进行补充或修订；若文件不存在，AI 必须根据用户输入先自动生成详细初稿。该文件仅承载业务需求，不写入设计说明或开发过程记录
- `doc/design/设计文档.md`：项目设计文档，全项目一份。包含架构设计、功能需求、界面原型与交互说明。由用户与 AI 协作产出，用户确认后作为开发的唯一需求基准。AI 可在文件中追加新功能章节，不删除已有内容，不新建平行文件

### requirement 要求
- 若 `doc/requirement.md` 为模板初始状态，AI 应根据用户输入将占位内容替换为项目真实需求，而不是长期保留“待补充”空壳。
- 需求文档建议固定包含以下章节：项目背景、目标与范围、用户角色、页面或模块清单、核心业务流程、关键数据与字段、权限与可见范围、边界场景与异常、非功能要求、待确认项。
- 自动生成需求文档时，优先写清业务事实、流程与边界，不提前写入技术实现方案。

### 回顾分析记录格式
- 适用场景：同类问题因规则缺口在同一任务中连续两次阻塞交付，或跨任务重复出现后，触发简短回顾分析时使用
- 内容保持简短，建议至少包含：
  - 错误现象
  - 触发场景
  - 根因
  - 本次补充或修改的规则
  - 后续如何避免或验证不再复发
