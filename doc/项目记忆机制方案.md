# 项目记忆机制方案

> 文档状态：待评审
>
> 编写日期：2026-09-15
>
> 适用范围：`fragments/shared/common/collaboration-AGENTS.md`（生成到全部组合的根规则）、可选的 `app/RuleAssembler` 初始化逻辑

## 1. 目标与定位

在生成到目标项目的规则中加入「项目记忆」机制：AI 在协作过程中遇到项目关键信息（业务术语、决策原因、外部约束、踩坑修复等）时，写入项目内固定目录；后续会话中用户提问时，AI 主动读取该目录作为跨会话上下文。

定位约束：

- 该机制是**增益而非依赖**：规则属软约束，命中率必然低于 100%，不能把它当作会话连续性的保证。
- 记忆是**项目公共知识资产**：随仓库提交、团队共享、跨工具一致（AGENTS.md / CLAUDE.md / GEMINI.md 由同一 shared 小节生成，行为相同），不与各工具的用户级原生记忆（如 Claude Code / ZCode 的 auto memory）混用——原生记忆管「该用户的私有偏好」，项目记忆管「这个项目沉淀的公共知识」。

## 2. 与既有记录类机制的关系

当前规则体系已有两个「写文件留痕」机制，项目记忆是第三条，三者目的、去处、git 策略互不重叠：

| 机制 | 记什么 | 写到哪里 | git 策略 |
|---|---|---|---|
| 重复问题回顾 | 规则缺口与预防措施 | 落实进规则文件本身 | 随规则提交 |
| 规则效果反馈 | 规则命中 / 违反 / 冗余信号 | `.ai-rule-feedback.md` | 本地待处理清单，已自动加 `.gitignore` |
| 项目记忆（本方案） | 项目知识本身（业务、决策、约束、踩坑） | `.ai-memory/` 目录 | **随仓库提交**，团队共享 |

反馈机制有回传承接口径（`doc/规则效果反馈承接.md`）是因为反馈要回到本仓库改规则；项目记忆始终留在目标项目内，不回传，因此只需本设计文档，不需要另立承接流程。

## 3. 机制设计

### 3.1 目录结构

```text
.ai-memory/
├── MEMORY.md            索引：一行一主题（主题 + 一句话摘要 + 文件链接），会话开始必读
└── <topic>.md           单主题记忆文件，按主题命名（如 payment-terms.md、tech-decisions.md）
```

- 目录与索引由 AI **首次写入时懒创建**，生成器不预先创建、不改动、不在 `--upgrade` 时覆盖其内容。
- 命名采用 `.ai-memory/`：与 `.ai-rule-profile.json`、`.ai-rule-feedback.md` 构成同一命名族；隐藏目录照常提交（同 `.github/`），是否提交由 git 策略决定而非目录可见性。备选 `docs/ai-memory/` 见 §7 开放问题。

### 3.2 记忆分类

值得记忆（写入前自查是否属于以下五类）：

1. 业务概念与术语定义：代码中分散或看不出来的领域规则；
2. 技术决策及其原因：为什么选 A 不选 B，含被否方案的否决理由；
3. 外部系统约束：依赖的服务、环境、账号位置（**不含凭据本身**）；
4. 非显而易见的踩坑与修复方案；
5. 用户明确要求「记住这个」的约定与偏好。

禁止写入：能从代码 / git 直接推导的内容、一次性任务细节、密钥 / 凭据 / 内部地址等敏感信息、与既有记忆重复的内容（走覆盖更新）。

### 3.3 写入规则

- **触发点**：任务收尾时检查本任务是否产生上述关键信息（与「规则效果反馈」同一触发点，收尾触发比聊天中途触发可靠）；会话中用户明确要求记住的内容即时写入。
- **更新语义**：同主题已有记忆文件则**覆盖更新该文件与索引行**，不追加重复文件、不无限堆条目——记忆是「当前为真的知识」，不是流水日志。
- **溯源**：每条记忆注明日期与来源（涉及文件或对话场景），主题文件头部使用统一的轻量 frontmatter（topic / created / updated）。

### 3.4 读取规则

- 会话开始且索引存在时先读 `MEMORY.md`，把握可用主题（索引常驻上下文，因此必须保持精炼）。
- 用户问到项目历史、决策原因、团队约定、「之前提到 / 之前说过」类问题时，先查对应主题文件再回答，引用记忆时注明来源文件。

### 3.5 治理规则

- **代码优先**：记忆与代码现状矛盾时以代码为准，完成任务前顺手修正对应记忆并更新索引——错误或过期的记忆被后续会话当事实用，比没有记忆更糟。
- **索引容量**：索引一行一主题、控制在数十行内，超出时优先合并相邻主题；详情按需读取，不整体载入。

## 4. 规则文本草案

以下为加入 `fragments/shared/common/collaboration-AGENTS.md` 的小节草案（置于「规则效果反馈」之后，行文风格与既有小节一致）：

```markdown
## 项目记忆
- 目标项目根目录 `.ai-memory/` 是跨会话的项目知识库：`MEMORY.md` 为索引（一行一主题 + 一句话摘要 + 文件链接），每个主题一个 `<topic>.md`；目录随仓库提交，首次写入时创建，生成器不改动其内容。
- 值得记忆的内容：业务概念与术语定义、技术决策及其原因、外部系统约束（不含凭据本身）、非显而易见的踩坑与修复、用户明确要求记住的约定；禁止写入密钥、凭据、内部地址等敏感信息，也不记录能从代码或 git 直接推导的内容。
- 写入时机：任务收尾时检查本任务是否产生上述关键信息（与「规则效果反馈」同一触发点），用户明确要求记住的内容即时写入；同主题已有记忆则覆盖更新该文件与索引行，不追加重复文件。每条记忆注明日期与来源（涉及文件或对话场景）。
- 读取时机：会话开始且索引存在时先读 `MEMORY.md` 把握可用主题；用户问到项目历史、决策原因、团队约定或「之前提到」类问题时，先查对应主题文件再回答，引用时注明来源文件。
- 记忆与代码现状矛盾时以代码为准，完成任务前顺手修正对应记忆并更新索引；索引一行一主题、保持在数十行内，超出时优先合并相邻主题。
```

## 5. 本仓库落地步骤

1. 登记：按 `RULE-YYYYMMDD-NAME` 任务 ID 建提交登记；归属按 `doc/规则效果反馈承接.md`「变更归属」表走 `shared/common/collaboration-AGENTS.md`（跨架构通用约束，改一处同步全部组合，不复制到 arch 片段）。
2. 修改：按 §4 草案新增小节；确认无重复标题（`--check` 守卫会校验）。
3. 验证：`--check` 全部兼容样例通过、`--emit` 基线差异逐一核验、单元测试通过。
4. 版本：规则内容变化，升 `vars.version` 并在提交信息中记录任务与验证结论。

生成器侧默认**零改动**（懒创建方案不需要初始化逻辑）；若 §7 决定生成时初始化空索引，再补 `RuleAssembler` 与对应测试。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 软约束命中率不足 100% | 定位为增益而非依赖；用收尾触发点提高可靠性，不追求聊天中途实时捕获 |
| 错误 / 过期记忆成为毒数据 | 覆盖更新语义 + 溯源标注 + 「代码优先、顺手修正」义务 |
| 上下文成本上升 | 仅索引常驻且限数十行，详情按需读取 |
| 敏感信息泄漏进仓库 | 规则显式禁止写入密钥 / 凭据 / 内部地址 |
| 目录退化为无人维护的流水账 | 单主题单文件 + 覆盖更新 + 索引容量约束，禁止把记忆当日志追加 |
| 与工具原生记忆机制重叠 | 定位区分（项目公共知识 vs 用户私有记忆），规则文本说明互补不迁移 |

## 7. 开放问题

1. **目录命名**：`.ai-memory/`（推荐，与 `.ai-rule-*` 命名族一致）vs `docs/ai-memory/`（对人类更可见、但与项目自有文档目录耦合）。
2. **生成器是否初始化**：默认懒创建零改动；备选生成 / 升级时创建 `.ai-memory/MEMORY.md` 空索引（好处是目录约定在仓库里可见，代价是 `RuleAssembler` 需新增逻辑与测试）。
3. **索引容量阈值**：暂以「数十行」软约束观察实际膨胀速度，不在规则中硬编码数字，必要时按规则效果反馈数据再定阈值。
