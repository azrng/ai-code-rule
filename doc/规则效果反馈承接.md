# 规则效果反馈承接流程

目标项目按生成规则中 `collaboration-AGENTS.md` 的「规则效果反馈」小节，把规则命中与违反情况记录到项目根目录 `.ai-rule-feedback.md`。本文件定义这些反馈回到 `fragments/` 的承接口径，处理反馈时遵循本文件，不临时另立口径。

## 反馈条目格式

与生成规则中的约定一致，每条目为一个二级标题：

```markdown
## [YYYY-MM-DD] 一句话主题
- 规则：<命中或违反的规则文件与小节，如 collaboration-AGENTS.md#任务管理>
- 类型：<违反 / 冲突 / 缺失 / 有用>
- 场景：<触发它的任务与情况>
- 说明与建议：<现象、原因、希望规则如何修改>
```

## 承接流程

1. 收集：从目标项目取回 `.ai-rule-feedback.md` 内容（用户粘贴、gitee issue 或 PR 均可）；同一条目被多个项目重复提出时合并处理。
2. 登记：在本仓库 `TASK.md` 建任务，逐条判断类型与影响面；「有用」类条目只聚合不立任务。
3. 归属：按 `TASK.md` §2.4「后续 AI Rule 变更归属」选择维护入口（`shared/`、family/skeleton、组件、capability 或显式 delta），不复制 Profile。
4. 落地：修改 `fragments/` 与 manifest；涉及新增技术类型或能力时，同步补检测映射、约束与回归样例（走扩展口清单）。
5. 验证与版本：`--check`、单元测试、`--emit` 基线差异逐一核验；规则内容变化必须升 `vars.version`。
6. 回执：在原目标项目的 `.ai-rule-feedback.md` 对应条目标注处理结果（规则版本号，或「不采纳 + 原因」）；该项目下次执行 `--upgrade` 即获得改进后的规则。

## 优先级与信号口径

- 「违反 / 冲突」优先于「缺失」处理；「缺失」优先于「有用」。
- 「有用」类条目聚合后作为高频命中信号，用于评估子规则的实际阅读率与拆分粒度，不直接触发规则修改。
- 不采纳的条目必须记录原因；同类反馈反复出现时重新评估原结论，而不是重复拒绝。
