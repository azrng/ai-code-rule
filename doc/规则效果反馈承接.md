# 规则效果反馈承接流程

目标项目按生成规则中 `collaboration-AGENTS.md` 的「规则效果反馈」小节，把规则命中与违反情况记录到项目根目录 `.ai-rule-feedback.md`。本文件定义这些反馈回到 `fragments/` 的承接口径，处理反馈时遵循本文件，不临时另立口径。

## 反馈条目格式

与生成规则中的约定一致，每条目为一个二级标题：

```markdown
## [YYYY-MM-DD] 一句话主题
- 规则：<命中或违反的规则文件与小节，并附该文件 front matter 的 version，如 collaboration-AGENTS.md#任务管理（v2.3.0）>
- 类型：<违反 / 冲突 / 缺失 / 有用 / 冗余>
- 场景：<触发它的任务与情况>
- 说明与建议：<现象、原因、希望规则如何修改>
```

## 承接流程

1. 收集：从目标项目取回 `.ai-rule-feedback.md` 内容（该文件已加入目标项目 `.gitignore` 不随项目提交，取回方式为用户粘贴文件内容或贴到 gitee issue）；同一条目被多个项目重复提出时合并处理。
2. 登记：按批次建 git 提交登记任务（提交信息以任务 ID 开头，如 `RULE-20260916-XXX`），逐条判断类型与影响面；「有用」类条目只聚合不立任务。
3. 归属：按下方「变更归属」表选择维护入口（`shared/`、family/skeleton、组件、capability 或显式 delta），不复制 Profile。
4. 落地：修改 `fragments/` 与 manifest；涉及新增技术类型或能力时，同步补检测映射、约束与回归样例（走扩展口清单）。整段重写或替换规则前，先用 `git log -p -- <规则源文件>` 和 `git diff HEAD -- <规则源文件>` 核对近期任务补丁与未提交条目，逐条保留或合并；确需退役的规则按 `doc/规则退役清单.md` 处理，不凭整段重写静默删除。在 `TASK.md` 对应任务目标中写明已落规则文件、章节标题与条目要点，便于后续更新核对。
5. 验证与版本：`--check`、单元测试、`--emit` 基线差异逐一核验；规则内容变化必须升 `vars.version`。定性「未修复 / 复发」前，必须先在源仓库按该样例 `--emit` 最新产物并核对命中文件 front matter 的 `version` 与内容——目标项目侧产物可能因本地修改被 `--upgrade` 保留为旧版，不得作为修复与否的事实源；门控类修改（新增某行为的强制 / 豁免条款）落地时必须全量检索反向语义（跳过、豁免、可选、简化路径）并逐一声明口径，`--check` 只验结构一致，不验语义覆盖面。
6. 回执：把处理结果（规则版本号，或「不采纳 + 原因」）回传给原目标项目，由其在 `.ai-rule-feedback.md` 中删除对应条目（该文件是待处理清单，只保留未处理反馈；处理结果随规则版本生效，不在文件内长期累积）；该项目下次执行 `--upgrade` 即获得改进后的规则。

## 变更归属

后续修改规则时，先按影响范围选择维护入口：

| 变更类型 | 首选维护位置 | 处理要求 |
| --- | --- | --- |
| 所有项目都适用的协作规则 | `fragments/shared/` 或根骨架 | 评估所有受影响 Profile，补全回归说明 |
| 某一项目形态或架构族共用规则 | 对应 family / skeleton 模块 | 只影响该族，禁止复制到每个 Profile |
| 单一技术栈规则 | `backend` / `frontend` / `shell` 组件 | 在 manifest 中声明适用条件和输出归属 |
| 可选能力规则 | `capability` 模块 | 用 feature ID 控制，不把能力写死进 Profile |
| 只有一个组合的真实差异 | 显式 delta 或兼容层 | 记录原因；若重复出现则转为独立组件 |

新增技术类型或能力的完整清单（manifest 声明、检测映射、约束、回归样例、版本与 README）见 `app/RuleAssembler/README.md` 的「新增模块清单」。

## 优先级与信号口径

- 「违反 / 冲突」优先于「缺失」处理；「缺失」优先于「有用」；「冗余」不参与该排序，按独立证据门槛进入规则退役评审。
- 「有用」类条目聚合后作为高频命中信号，用于评估子规则的实际阅读率与拆分粒度，不直接触发规则修改。
- 「冗余」类条目必须有可比较的同类任务证据；达到 `doc/规则退役清单.md` 的门槛后，才进入压缩或退役评审，不直接删除规则。
- 不采纳的条目必须记录原因；同类反馈反复出现时重新评估原结论，而不是重复拒绝。
