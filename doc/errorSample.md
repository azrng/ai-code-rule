## 十五个误区全面总结

### 一、内容层面的误区 (3个)

| 误区 | 描述 | 正确做法 |
|------|------|----------|
| **百科全书式** | 写成几千行的大文档，试图包含所有知识 | 保持 100-300 行的索引式文档，只放地图不写全书 |
| **过度解释基础** | 详细解释"什么是 React"、"什么是 Git"等常识 | 假设 AI 有常识，只写项目特定规则 |
| **包含完整内容** | 像 llms.txt 一样包含所有页面内容 | 指向详细文档位置，而非包含所有内容本身 |

---

### 二、结构管理层面的误区 (3个)

| 误区 | 描述 | 正确做法 |
|------|------|----------|
| **单文件膨胀** | 单文件超过 100-300 行，token 消耗激增 | 分层管理：全局 → 仓库级 → 子目录独立文件 |
| **混淆临时与持久** | 把临时提示词当成持久规则，或反之 | 事后迭代更新，而非事前完美设计 |
| **缺乏版本控制** | 不纳入版本控制，团队无法共享 | 像 `.gitignore` 一样维护，团队共享积累的经验 |

---

### 三、使用策略层面的误区 (3个)

| 误区 | 描述 | 正确做法 |
|------|------|----------|
| **预防性编程** | 试图预先列出所有规则防止 AI 犯错 | **验证比指令更重要** — 投资测试套件、linter、CI |
| **AI 自生成文档** | 让 Agent 自己生成 AGENTS.md | 人工审核、精简关键信息 |
| **忽视错误驱动** | 事前设计完美文档 | **当 AI 犯同样错误两次时**，让它做回顾分析后更新 |

---

### 四、上下文管理层面的误区 (2个)

| 误区 | 描述 | 正确做法 |
|------|------|----------|
| **会话管理混乱** | 一个项目单线程、不清理历史 | 一任务一线程，及时 `/compact` / `/clear` |
| **过度预加载** | 每次让 AI 读取所有文件 | 让 Agent 用 `glob`/`grep` 按需搜索（可省 10万+ token）|

---

### 五、架构设计层面的误区 (3个)

| 误区 | 描述 | 正确做法 |
|------|------|----------|
| **单 Agent 扛所有** | 一个 Agent 做前端、后端、基建等所有任务 | 为不同任务创建专门的子 Agent 或 Skill |
| **工具设计极端** | 过度原子化或过度聚合 | 平衡工具设计 |
| **忽视 Compact** | 压缩后不标注哪些信息绝对不能丢 | 明确标注架构决策、已修改文件、验证状态等关键信息 |

---

### 六、安全权限层面的误区 (1个)

| 误区 | 描述 | 正确做法 |
|------|------|----------|
| **过度权限** | 给 Agent 不需要的功能或过高权限 | **最小权限原则**，高风险操作需人工确认 |

---

## 核心原则总结

```
把 AGENTS.md 写成地图，不是百科全书
列出项目结构、核心模块、关键约定
指向详细文档位置
```

Agent 需要的是"**去哪里找信息**"，不是"**所有信息都在这里**"。

## 最佳实践对照表

| ❌ 误区 | ✅ 正确做法 |
|--------|-----------|
| 百科全书式的大文档 | 100-300 行的索引式文档 |
| 预防性列出所有规则 | 错误驱动、事后迭代更新 |
| 单文件管理所有任务 | 分层管理：全局 → 仓库级 → 子目录 |
| 让 AI 自己生成文档 | 人工审核、精简关键信息 |
| 包含详细基础知识 | 假设 AI 有常识，只写项目特定规则 |
| 忽视验证机制 | 投资测试、lint、CI 等反馈基础设施 |
| 混乱的会话管理 | 一任务一线程，及时 compact/clear |

---

## 精彩引述

> "验证比指令更重要" — 投资测试套件、linter、CI 管道等基础设施，比写冗长的预防性规则更有效。

> "当 AI 犯同样错误两次时，让它做回顾分析，然后更新 AGENTS.md" — AGENTS.md 应该是事后总结的产物，而非事前设计的完美文档。
