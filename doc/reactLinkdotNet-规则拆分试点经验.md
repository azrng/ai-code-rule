# reactLinkdotNet 规则拆分试点经验

## 背景

本文件最初用于记录 `reactLinkdotNet` 的规则拆分试点结果。  
经过后续几轮收敛，这套经验已经从“单次试点记录”演变为“可直接复用到其他模板的拆分方法总结”，因此这里同步更新为当前可执行版本。

---

## 试点结果与当前结论

`reactLinkdotNet` 最终验证下来的可用结构，不再是“目录 + AGENTS.md”，而是：

- 根入口：`reactLinkdotNet/AGENTS.md`
- 前端规则：`reactLinkdotNet/frontend-AGENTS.md`
- 后端规则：`reactLinkdotNet/backend-AGENTS.md`
- 文档规则：`reactLinkdotNet/doc-AGENTS.md`
- 基础设施规则：`reactLinkdotNet/infra-AGENTS.md`

也就是说，当前结论已经从早期试点阶段的“目录表达作用域”收敛为：

- 根文件继续固定为 `AGENTS.md`
- 子规则统一使用 `<scope>-AGENTS.md`
- 只有当某个作用域未来确实需要承载多份文件时，才恢复成独立目录

这个命名方式的优势更稳定：

- 目录层级更浅，资源管理器里一眼能看到全部子规则
- 不会出现大量“只为了包一个 `AGENTS.md` 而存在”的空壳目录
- 复制模板、查找规则、做仓库级维护都更轻

---

## 已验证可推广的模板

截至目前，这套拆分方式已经实际落地并验证在以下模板中：

- `reactLinkdotNet`
- `avaloniaExe`
- `dotnetCoreSingle`
- `dotnetLayered`
- `dotnetBlazor`

其中：

- `reactLinkdotNet`、`dotnetBlazor` 这类存在明显“界面 / 服务 / 文档 / 基础设施”边界的模板，适合拆成 4 个或更多子规则
- `dotnetCoreSingle`、`dotnetLayered` 这类后端主导模板，更适合拆成 `backend-AGENTS.md`、`doc-AGENTS.md`、`infra-AGENTS.md`
- `avaloniaExe` 这类桌面端模板，可以按 `ui-AGENTS.md`、`application-AGENTS.md`、`infrastructure-AGENTS.md`、`doc-AGENTS.md` 拆分

---

## 拆分判断原则

- 根 `AGENTS.md` 只保留全局都需要先读的内容，不再承载大段实现细则
- 只有在明显具备独立作用域时才拆出子文件，避免拆得过碎
- 子规则统一命名为 `<scope>-AGENTS.md`
- 根文件必须能让 AI 快速知道“还要读什么”，所以必须补齐子规则索引和阅读顺序
- 新增的“重复错误回顾与规则更新机制”应放在根入口，避免遗漏
- 拆分后根文件仍然要保留“开发流程总览”和“使用方式”，不能瘦身到只剩一个目录索引

## 根文件职责

### 根 `AGENTS.md` 应保留

- 目标
- 工作方法
- 注意事项
- 子规则索引
- 子规则阅读顺序
- 开发流程总览
- 使用方式
- 任务类型阅读策略
- 核心规则
- 验证优先级规则
- 思考与实现原则
- 编码规则
- 任务管理机制
- Git 与提交流程
- 交付收口规范
- 高风险操作确认规则
- 常见禁止事项
- 交付输出要求
- 重复错误回顾与规则更新机制

### 根 `AGENTS.md` 不再保留

- 技术栈细则
- 推荐目录结构明细
- 阶段 0 设计细则
- 设计系统细则
- 接口契约细则
- Docker 细则
- 前端 / 后端 / UI / Application / Infrastructure 规则全文
- 各层测试细则
- 文档维护细则

## 子规则职责划分

### `ui-AGENTS.md` / `frontend-AGENTS.md`

承载内容通常包括：

- 界面技术栈
- 设计系统相关约束
- 推荐目录结构
- 页面 / 组件 / 布局 / 样式 / 状态管理规则
- 界面测试规则

### `backend-AGENTS.md`

承载内容通常包括：

- 后端技术栈
- 核心库
- 依赖注入规范
- 推荐目录结构
- 分层或单体后端实现规则
- 数据访问、缓存、Swagger、异常处理规则
- 后端测试规则

### `application-AGENTS.md`

适用于桌面端或分层明确但不完全等同 Web 后端的模板，承载内容通常包括：

- ViewModel / Service / Model 的职责边界
- 业务编排规则
- DTO 和结果包装约束
- 应用层测试规则

### `infrastructure-AGENTS.md` / `infra-AGENTS.md`

承载内容通常包括：

- 部署方式
- 默认端口
- Docker / Compose 规则
- 环境变量与发布链路约束
- 数据库迁移或运行环境说明

### `doc-AGENTS.md`

承载内容通常包括：

- 阶段 0 设计文档要求
- 接口契约规范
- `design-system.yaml` 规则
- 文档更新要求
- `requirement` / `devlog` / 回顾记录格式

## 这次试点真正有效的做法

- 先拆“索引和入口”，再拆“细则内容”，这样不容易把规则整体打散
- 根文件里保留“开发流程总览”，而不是完全删掉开发流程，能降低阅读跳转成本
- 子文件开头补“适用范围”和“触发场景”，比只给文件名更清晰
- 先试点一个架构，再逐步推广到相似模板，比一开始全仓批量改更稳
- 目录式拆分验证完可行后，再收敛到扁平命名，比一开始就纠结命名更高效

---

## 试点后的二次收敛

在第一轮完成拆分后，又根据错误样例和真实维护体验做了二次补强。最终确认值得一起推广的规则有：

- 验证优先级规则：验证比单纯指令更重要，能靠测试、lint、构建、Swagger、smoke test、容器化验证证明的内容，不要只靠文字约束
- 按需阅读规则：不要每次预读所有文件，优先通过索引、目录和搜索定位命中的规则文件，再按需阅读
- 任务类型阅读策略：不同任务优先读取不同子规则，联调任务必须同时读根文件和相关子规则
- 跨关注面任务拆分规则：若任务明显跨前后端、跨界面与服务、跨业务与部署，先拆子任务再执行，不要混在一个实现步骤里
- 高风险操作确认规则：删除、批量重构、数据库破坏性变更、清理环境前，必须先确认
- 回顾分析落地格式：回顾记录保持简短，至少写清错误现象、触发场景、根因、本次补充或修改的规则、后续如何避免或验证不再复发

## 这次遇到的问题

### 1. 中文内容处理容易受终端编码影响

- 直接在终端里做字符串切分时，容易因为显示编码问题误判章节标题
- 更稳妥的方式是基于文件本身的 UTF-8 内容处理，而不是依赖终端显示结果

### 2. 生成式改写容易残留重复分隔符

- 原始单文件里已经有 `---`，拆分时如果直接拼接，很容易出现重复分隔线
- 拆分后要专门做一轮结构检查，确认没有多余的分隔线、重复标题和重复说明

### 3. 根文件过度瘦身会影响可读性

- 如果把开发流程、使用方式也全部下放，根文件虽然更短，但会失去入口文件的引导作用
- 实际上根文件仍然需要保留“先读就能开始协作”的基础信息

### 4. 只拆结构，不补阅读与验证规则，仍然会反复出错

- 仅把大文件拆小，并不能自动解决 AI 误读、漏读和重复犯错的问题
- 拆分完成后，还需要补“先读索引再按需读子规则”“验证优先于补更多规则”“同类错误二次出现后做回顾”这类执行规则

### 5. 目录式命名在模板仓里维护成本偏高

- 当子目录里只有一个 `AGENTS.md` 时，目录结构本身不承载额外信息
- 继续保留目录层只会增加点击成本和查找成本
- 因此最终统一改成扁平命名是更适合本仓库的收敛方向

---

## 后续推广建议

- 后续改其他架构时，优先沿用这次已经验证过的入口结构
- 不要再回到“目录 + `AGENTS.md`”的子规则命名，默认直接使用 `<scope>-AGENTS.md`
- 推广时不要只复制目录结构，也要一起复制验证优先级、按需阅读、高风险确认和回顾格式这几类规则
- 批量推广时，优先处理结构最接近的模板
- 若后续新增模板，先判断作用域边界是否明确，再决定拆成 3 个、4 个还是更多子规则

---

## 建议的复用步骤

1. 先确认该架构适合拆成哪些作用域文件。
2. 保留根 `AGENTS.md` 作为唯一入口。
3. 先补子规则索引、阅读顺序、重复错误回顾机制。
4. 再补验证优先级、按需阅读、任务类型阅读策略和高风险确认规则。
5. 再将技术栈、实现细则、测试细则、文档细则分别下放。
6. 在 `doc-AGENTS.md` 或等价文档子规则中补一个简短的回顾分析记录格式。
7. 拆分后逐个检查是否存在重复内容、缺失规则和阅读断层。
8. 若子规则只是单文件承载，统一使用 `<scope>-AGENTS.md` 扁平命名。
9. 最后按一次真实任务流程检查可读性与命中体验。

---

## 当前可直接复用的结论

如果后续要继续拆分新的模板，可以直接套用以下默认策略：

- Web 前后端分离模板：`frontend-AGENTS.md` + `backend-AGENTS.md` + `doc-AGENTS.md` + `infra-AGENTS.md`
- 单体 Web API 模板：`backend-AGENTS.md` + `doc-AGENTS.md` + `infra-AGENTS.md`
- 分层后端模板：`backend-AGENTS.md` + `doc-AGENTS.md` + `infra-AGENTS.md`
- 桌面端模板：`ui-AGENTS.md` + `application-AGENTS.md` + `infrastructure-AGENTS.md` + `doc-AGENTS.md`
- Blazor 一体化模板：`ui-AGENTS.md` + `backend-AGENTS.md` + `doc-AGENTS.md` + `infra-AGENTS.md`

这份文档后续不再只代表 `reactLinkdotNet` 单个模板，而是作为当前这一轮规则拆分的通用经验基线。
