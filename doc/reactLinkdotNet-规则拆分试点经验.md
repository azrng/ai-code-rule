# reactLinkdotNet 规则拆分试点经验

## 背景

本次先以 `reactLinkdotNet` 为试点，将原本单文件的 `AGENTS.md` 拆分为“根入口 + 子规则文件”的结构，用来验证后续是否适合批量推广到其他架构模板。

## 本次拆分结果

- 根入口：`reactLinkdotNet/AGENTS.md`
- 前端规则：`reactLinkdotNet/frontend/AGENTS.md`
- 后端规则：`reactLinkdotNet/backend/AGENTS.md`
- 文档规则：`reactLinkdotNet/doc/AGENTS.md`
- 基础设施规则：`reactLinkdotNet/infra/AGENTS.md`

## 拆分判断原则

- 根 `AGENTS.md` 只保留全局都需要先读的内容，不再承载大段前后端细则。
- 只有在明显具备独立作用域时才拆出子文件，避免拆得过碎。
- 子文件继续统一命名为 `AGENTS.md`，通过目录名表达作用域。
- 根文件必须能让 AI 快速知道“还要读什么”，所以必须补齐子规则索引和阅读顺序。
- 新增的“重复错误回顾与规则更新机制”应放在根入口，避免遗漏。

## 各文件职责划分

### 根 `AGENTS.md`

保留内容：

- 目标
- 工作方法
- 注意事项
- 子规则索引
- 子规则阅读顺序
- 开发流程总览
- 使用方式
- 核心规则
- 思考与实现原则
- 编码规则
- 任务管理机制
- Git 与提交流程
- 交付收口规范
- 常见禁止事项
- 交付输出要求
- 重复错误回顾与规则更新机制

不再保留内容：

- 前端技术栈细则
- 后端技术栈细则
- 推荐目录结构明细
- 阶段 0 设计细则
- 接口契约细则
- Docker 细则
- 前端规则与后端规则全文
- 前后端测试细则
- 文档维护细则

### `frontend/AGENTS.md`

承载内容：

- 前端技术栈
- 设计系统相关前端约束
- 前端推荐目录结构
- 前端规则
- 前端测试规则

### `backend/AGENTS.md`

承载内容：

- 后端技术栈
- 核心库

- 后端推荐目录结构
- Clean Architecture 后端规则
- 后端测试规则

### `doc/AGENTS.md`

- 文档更新要求

### `infra/AGENTS.md`

- Docker 规则

## 这次试点的有效做法

- 先拆“索引和入口”，再拆“细则内容”，这样不容易把规则整体打散。
- 根文件里保留“开发流程总览”，而不是完全删掉开发流程，能降低阅读跳转成本。
- 子文件开头补“适用范围”和“触发场景”，比只给文件名更清晰。
- 先试点一个架构，而不是一次性批量改所有模板，能更快发现结构问题。

## 试点后的二次收敛

在第一轮完成拆分后，又根据错误样例对 `reactLinkdotNet` 做了一轮补强，结论是：拆分结构之外，还需要补齐“怎么读、怎么验证、什么操作要确认、怎么做回顾”。

本次新增并确认值得推广的规则有：

- 验证优先级规则：验证比单纯指令更重要，能靠测试、lint、构建、Swagger、smoke test 证明的内容，不要只靠文字约束。
- 按需阅读规则：不要每次预读所有文件，优先通过索引、目录和搜索定位命中的规则文件，再按需阅读。
- 任务类型阅读策略：前端任务优先读 `frontend/AGENTS.md`，后端任务优先读 `backend/AGENTS.md`，联调任务必须同时读根文件、`frontend`、`backend`、`infra`。
- 跨前后端任务拆分规则：若任务明显跨前后端，先拆子任务再执行，不要混在一个实现步骤里。
- 高风险操作确认规则：删除、批量重构、数据库破坏性变更、清理环境前，必须先确认。
- 回顾分析落地格式：回顾记录保持简短，至少写清错误现象、触发场景、根因、本次补充或修改的规则、后续如何避免或验证不再复发。

## 这次遇到的问题

### 1. 中文内容处理容易受终端编码影响

- 直接在终端里做字符串切分时，容易因为显示编码问题误判章节标题。
- 更稳妥的方式是基于文件本身的 UTF-8 内容处理，而不是依赖终端显示结果。

### 2. 生成式改写容易残留重复分隔符

- 原始单文件里已经有 `---`，拆分时如果直接拼接，很容易出现重复分隔线。
- 拆分后要专门做一轮结构检查，确认没有多余的分隔线、重复标题和重复说明。

### 3. 根文件过度瘦身会影响可读性

- 如果把开发流程、使用方式也全部下放，根文件虽然更短，但会失去入口文件的引导作用。
- 实际上根文件仍然需要保留“先读就能开始协作”的基础信息。

### 4. 只拆结构，不补阅读与验证规则，仍然会反复出错

- 仅把大文件拆小，并不能自动解决 AI 误读、漏读和重复犯错的问题。
- 拆分完成后，还需要补“先读索引再按需读子规则”“验证优先于补更多规则”“同类错误二次出现后做回顾”这类执行规则。

## 后续推广建议

- 后续改其他架构时，优先沿用这次试点的入口结构。
- 在真正批量推广前，先让使用者测试 `reactLinkdotNet` 这一版的可读性和执行体验。
- 若测试中发现 AI 仍然经常漏读子规则，需要进一步强化根文件中的索引格式和阅读顺序描述。
- 推广时不要只复制目录结构，也要一起复制验证优先级、按需阅读、高风险确认和回顾格式这几类规则。
- 批量推广时，应优先处理结构最接近的模板，例如 `vueLinkdotNet`。

## 建议的复用步骤

1. 先确认该架构适合拆成哪些作用域目录。
2. 保留根 `AGENTS.md` 作为唯一入口。
3. 先补子规则索引、阅读顺序、重复错误回顾机制。
4. 再补验证优先级、按需阅读、任务类型阅读策略和高风险确认规则。
5. 再将技术栈、实现细则、测试细则、文档细则分别下放。
6. 在 `doc/AGENTS.md` 中补一个简短的回顾分析记录格式。
7. 拆分后逐个检查是否存在重复内容、缺失规则和阅读断层。
8. 最后让真实使用者按一次完整任务流程测试可用性。
