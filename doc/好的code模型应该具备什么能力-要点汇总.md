# 好的 Code 模型应该具备什么能力 — 要点汇总

> 来源：[鹅厂员工觉得好的code模型应该具备什么能力？](https://mp.weixin.qq.com/s/1hAg9mNr1g6MKx0Om8osQg)（腾讯技术工程，2026-05-09）

## 1. "懂得不写代码"的智慧

- 模型应能识别已有工具库和现成实现，避免重复造轮子（如已有缓存/Dao就不要自己实现）
- 最高级的能力是**判断什么时候不该写代码**：建议用户直接用现有库、指出思路问题、推荐更合适的模式
- 生成代码 ≠ 狂写代码，判断力比单纯生成更难、更有价值

## 2. 先学后写，模仿式开发

- 让 agent 先学习项目中类似功能的实现架构和 API 调用规范
- 总结出技术方案后再开始写代码，质量显著提升
- AI 本质上是"CV工程师"，给它好的模板才能产出好的代码

## 3. 需求理解与 Plan 机制

- 不能期望"一句话开发"——真实需求都是细节化的，需要模型与用户反复对齐
- 推荐做法：**让模型先给 plan，双方修改到共识后再动手**
- 好的开始是成功的一半

## 4. 可读性优先的代码风格

- 宁可生成慢一点、长一点，也要保证可读性
- 可读性差的代码质量往往也堪忧
- 浪费用户理解时间的代码不是好代码

## 5. 真正的调试能力（而非叠垃圾）

- 与其要求一次写对，不如要求**能真正修好有错误的代码**
- 不能看到一个 Error 就加 try-except 分支——那叫"叠垃圾"
- 模型可以 24h 高速运行，试错成本低，但要确保每次修复是正确的

## 6. LLM 友好的开发环境

- 需要一个能串联需求理解→代码生成→调试三个过程的环境
- 给模型足够的资源（工具、上下文、执行能力）
- 最好能辅助做 Context 工程

## 7. 看懂现有代码，保持风格一致

- 能理解现有代码的习惯和风格，生成代码时别瞎改
- 出问题能看报错秒懂原因，直接修复
- 发现重复或低效代码时给出更优雅的写法

## 8. 不知道就说不知道

- 不能胡编乱造，不知道就老实说不知道
- 瞎编代码坑人是最大的信任杀手

## 9. 调试和修 Bug 是当前最短板

- 微软研究：Claude、GPT 等模型调试成功率不到 50%，有的仅 20%
- 一个 bug 修完冒出三个新 bug（"打地鼠"现场）
- 处理复杂业务逻辑时容易"想当然"，按训练数据模式套，忽略公司独特规则
- 上下文有限，跨文件改动容易"丢三落四"
- Claude 的 debug 模式是一个值得探索的方向

## 10. 长上下文 + 高准确率 Function Calling

- 支持 200k+ 上下文（Codex 已支持 400k），长时异步任务越来越多
- Function Calling 参数格式必须高准确率，否则执行容易出错
- 高 Cache 能力降低长任务成本
- 低延时，补全和 NES 场景要求更高

## 11. Thinking 能力 + 多模态能力

- 需要能做好规划和反思，而非盲目生成
- 语音和图片输入需求越来越多（如 UAT 测试自动截图反馈场景）
- 编码范式正在改变，多模态是必然趋势

## 12. 架构感知能力

- 模型应理解项目整体结构，生成代码符合当前项目设计规范
- 能站在整个项目角度思考模块划分、分层设计、依赖关系
- 避免"头痛医头"——只答一段代码，不管全局

## 13. 上下文一致性

- 大工程里保持命名风格、设计模式、模块职责的一致性
- 不要前后矛盾，前面改了后面忘

## 14. 主动提醒和架构建议

- 发现耦合过重、职责不清时，主动给出架构层面的优化建议
- 不只是被动生成，而是主动参与设计决策

## 15. 架构设计能力短期内仍靠人

- AI 可以当好帮手，但开发者的架构思维和工程素养在 AI 时代反而更重要
- 基础架构没搭好，后面越写越乱，重构成本比重写还高
