# 好的 Code 模型应该具备什么能力 - 评估清单

> 来源：[鹅厂员工觉得好的code模型应该具备什么能力？](https://mp.weixin.qq.com/s/1hAg9mNr1g6MKx0Om8osQg)（腾讯技术工程，2026-05-09）
>
> 说明：本文从原始讨论中整理为评估清单，不只保留观点摘要，而是尽量保留可观察行为、典型失败模式和评估边界，便于后续横向比较不同 Code 模型或 Agent 产品。

## 1. 需求理解与澄清能力

- 能识别用户需求中的缺口、歧义、前置条件和隐含约束，而不是直接按一句话开始生成代码。
- 能在动手前给出可确认的 plan，说明实现步骤、影响范围、待确认问题和预期产出。
- 能根据用户反馈调整 plan，并在达成共识后再进入实现阶段。
- 评估时可观察：是否主动追问关键细节；是否遗漏边界条件；是否在需求未明确时贸然修改代码。

## 2. “懂得不写代码”的判断力

- 能识别项目中已有工具库、公共模块、缓存、Dao、SDK、框架能力和现成实现，优先复用而不是重复造轮子。
- 能判断用户提出的实现方式是否过度复杂、容易踩坑或偏离真实目标，并主动建议更简单、更合适的方案。
- 能在必要时明确告诉用户“不需要新增代码”“直接配置即可”“复用已有能力即可”。
- 评估时可观察：是否产生重复实现；是否忽略已有封装；是否为了完成任务而引入不必要的新抽象。

## 3. 项目学习与模仿式开发能力

- 能先阅读相似功能，学习项目的目录结构、API 调用方式、错误处理、数据访问、测试写法和命名习惯。
- 能基于已有实现归纳出当前项目的开发范式，再生成符合项目习惯的代码。
- 能避免把训练数据中的通用写法生搬硬套到当前项目。
- 评估时可观察：是否先检索同类实现；是否复用项目内约定；是否生成与项目风格明显割裂的代码。

## 4. 代码生成质量与可读性

- 生成代码应命名清晰、职责单一、结构直接，避免晦涩技巧、过度压缩和难以维护的控制流。
- 宁可实现稍长，也要让后续维护者容易理解；可读性差通常意味着质量风险更高。
- 应避免巨型函数、巨型类、超大页面基类和混杂多个无关职责的实现。
- 评估时可观察：代码是否容易审查；是否有清晰边界；是否为局部需求引入过大复杂度。

## 5. 现有代码理解能力

- 能准确理解已有业务逻辑、调用链、依赖关系、状态流转和隐含约束，而不是只看局部代码片段。
- 能理解报错、日志、测试失败和运行结果背后的真实原因。
- 能识别重复代码、低效实现和潜在维护问题，并给出符合当前项目的优化方式。
- 评估时可观察：是否误读业务规则；是否改错调用链；是否只修表象而没有定位根因。

## 6. 风格一致性与最小扰动能力

- 生成代码应保持现有命名风格、目录约定、框架习惯、设计模式和模块边界。
- 修改时应聚焦任务目标，避免无关重构、无关格式化、无关依赖升级和大面积改动。
- 在跨文件改动中，应保持前后实现一致，避免前面改了后面忘。
- 评估时可观察：diff 是否聚焦；是否破坏已有风格；是否引入不必要的文件变更。

## 7. 调试与修 Bug 能力

- 能根据报错、日志、测试失败、复现步骤和相关代码定位根因，并做最小正确修复。
- 不能通过随意加 try-catch、空判断、吞异常、绕过校验等方式“叠垃圾”。
- 修复后应能运行相关验证，确认没有引入新的回归问题。
- 评估时可观察：是否解释根因；是否只压制错误；是否一个 bug 修完引出更多 bug。

## 8. 复杂业务规则处理能力

- 面对公司内部规则、特殊流程、历史兼容逻辑和跨模块业务约束时，不能按通用训练模式想当然。
- 能在缺少业务上下文时主动指出不确定点，并通过阅读代码、测试、文档或询问用户补足信息。
- 能在多文件、多模块改动中保持业务语义一致。
- 评估时可观察：是否编造业务规则；是否忽略边界场景；是否只满足表面用例但破坏真实流程。

## 9. 可信输出与抗幻觉能力

- 不知道、不确定或上下文不足时，应明确说明不确定性，而不是编造 API、文件、依赖、配置、测试结果或业务结论。
- 对依赖版本、框架行为、外部接口、命令输出等可验证信息，应优先通过工具或资料确认。
- 对推断性结论应说明依据和限制，避免把猜测写成事实。
- 评估时可观察：是否引用不存在的函数；是否声称运行了未运行的测试；是否在缺少证据时给出肯定结论。

## 10. 工具调用与执行可靠性

- Function Calling、命令执行、文件编辑、测试运行、浏览器操作等工具调用应参数准确、格式稳定、错误处理清晰。
- 能正确理解工具返回结果，并根据失败信息调整下一步，而不是重复执行无效操作。
- 对长任务应能分阶段推进，保留关键上下文和中间结论。
- 评估时可观察：是否频繁传错参数；是否误读命令输出；是否在工具失败后继续基于错误假设推进。

## 11. 长上下文与任务持续能力

- 能处理大仓库、多文件、长对话和长时间异步任务，保持需求、约束、已修改文件和待办事项不丢失。
- 能在上下文较长时抓住关键约束，而不是被无关历史干扰。
- 能在跨轮沟通中保持前后一致，避免重复劳动和遗漏用户最新指令。
- 评估时可观察：是否遗忘早期约束；是否遗漏已改文件；是否忽略用户后续修正。

## 12. 规划、反思与自我校验能力

- 能先规划、再执行、再校验；任务复杂时能拆分阶段并持续更新状态。
- 能发现自身方案中的风险、矛盾和遗漏，并主动修正。
- 完成后能给出高信号总结，包括修改范围、验证结果、残余风险和后续建议。
- 评估时可观察：是否一路生成到底；是否缺少完成后的自查；是否发现问题后仍坚持错误方向。

## 13. 多模态理解能力

- 能理解截图、设计稿、报错图片、页面视觉反馈、语音或其他非文本输入，并转化为正确的代码修改或测试判断。
- 在前端、UAT、视觉回归和交互问题中，能结合图像信息判断布局、状态、样式和异常现象。
- 多模态输入不足以直接下结论时，应说明需要补充的上下文。
- 评估时可观察：是否能从截图定位问题；是否误解视觉状态；是否能把图片反馈落到具体代码变更。

## 14. 架构感知与工程一致性

- 能理解项目整体结构、分层设计、模块职责、依赖方向和扩展边界。
- 生成代码应符合当前项目设计规范，避免只解决局部问题却破坏整体架构。
- 发现耦合过重、职责不清、重复实现、依赖倒置或边界被破坏时，应主动提醒并提出可落地的调整方案。
- 评估时可观察：是否站在全局设计上思考；是否把无关职责塞进同一模块；是否能提出结构性改进建议。

## 15. 配套环境适配能力

- 这一项不是纯模型能力，而是 Code Agent 或开发平台能力；评估 Claude Code、Codex、Cursor、Gemini CLI 等产品时应单独记录。
- 理想环境应能串联需求理解、代码检索、文件编辑、命令执行、测试运行、浏览器验证、日志读取和上下文管理。
- 环境还应支持足够好的 Context 工程，例如代码索引、历史压缩、任务状态记录、工具权限控制和成本控制。
- 评估时可观察：模型是否能有效利用环境资源；环境是否限制模型发挥；失败到底来自模型本身还是工具链不足。

## 评估边界：架构设计短期内仍需要人把关

- Code 模型可以成为高效助手，但复杂系统的架构取舍、组织约束、长期演进和责任边界仍需要有工程经验的人审查。
- 基础架构没有搭好时，模型越能高速生成代码，越可能放大后续维护成本。
- 因此评估 Code 模型时，不应只看“写了多少代码”，还应看它是否能帮助人减少错误决策、降低维护成本，并在超出能力边界时主动暴露风险。
